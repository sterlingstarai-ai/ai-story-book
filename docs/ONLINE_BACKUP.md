# 온라인 백업

## 목적과 경계

기존 백업은 API·워커를 멈추고 DB·미디어 쓰기 잠금을 원격 게시까지 유지했다. 새 `--capture-mode online` 경로는 서비스 프로세스를 그대로 유지하며, 짧은 기준 시점 확정 이후의 복사·업로드 동안 정상 DB·미디어 쓰기를 허용한다. 오프라인 백업과 재해 복구 코드는 보존하며 자동으로 오프라인 방식으로 전환하지 않는다.

서비스 중지 없음은 DB 잠금 지연까지 항상 0이라는 뜻이 아니다. 정상 실행의 기준 시점 확정에는 2초 마감과 소켓 watchdog을 적용한다. 앱 미디어 쓰기의 기존 5초 제한은 바꾸지 않는다. 백업 프로세스 전체가 정지해 watchdog도 멈추는 경우는 PostgreSQL의 별도 statement/idle 제한으로 연결을 종료한다. 이 서버 보호와 아래의 특정 정지 시험 결과를 모든 장애에서 전체 잠금 시간이 2초 이내라는 보장으로 확대하지 않는다.

## 일관성 확보

1. 같은 실행 이미지에 등록된 API 소스를 사용하고, 두 DB 연결과 저장소 클라이언트를 잠금 밖에서 준비한다. 개인정보 저널도 미리 읽는다.
2. 미디어 advisory 잠금은 즉시 시도하고 테이블 잠금도 `NOWAIT`로 잡는다. 확보하지 못하면 백업만 제한적으로 재시도한다. 이 시점의 생성 작업·파기 작업·미게시 개인정보 이력·미해결 미디어 intent가 남아 있으면 기준 시점을 채택하지 않는다.
3. 같은 DB 스냅샷 S의 유휴 상태와 완전한 미디어 목록 T를 확보한다. 미리 연결한 read-only repeatable-read 세션이 S를 가져와 S2를 내보낸 뒤 원래 쓰기 잠금을 해제하고 실제 잠금 부재를 조회한다.
4. 잠금 해제 후에도 살아 있는 원래 S2 세션에서 스키마, 개인정보 outbox 전체의 게시 완료·연속 revision·정확한 내용 H0와 미디어 참조 완전성을 검사한다. 큰 검증 결과를 지역 간 전송하는 동안 쓰기를 막지 않되, 읽는 데이터는 여전히 S와 같다. 다섯 고정 조회를 하나의 SELECT로 묶고 위치·타입을 보존한 결과에 기존 검증 함수를 적용한다. 정확히 미리 읽은 SQL만 허용하며 새 연결의 현재 DB로 대체하지 않는다. 전체 검증 전에는 dump·업로드·완료 표식·성공 기록을 만들지 않는다. 실패하면 세션을 닫고 새 기준 시점으로 제한적으로 재시도한다.
5. `pg_dump --snapshot=S2`로 DB를 캡처한다. 운영 GCS의 기존 HMAC으로 T의 generation·metageneration을 고정한다. 다운로드는 그 세대와 메타데이터 세대 조건, ETag·크기·시각·원본 MD5를 확인한다. 다른 세대로 재요청하지 않는다. 원본이 바뀌거나 없어지면 백업만 실패하며 서비스는 유지한다.
6. 게시 전 새 DB 세션에도 바로 S2를 가져와 기존 `verify_backup_checkpoint()`로 S 전체 outbox와 H0를 대조한다. 현재 live DB가 달라졌다고 임의 부분 집합을 허용하거나 기존 전체 일치 검사를 약화하지 않는다. 파일·원격 체크섬과 서비스 identity를 확인한 경우에만 마지막 완료 표식을 게시한다.

원격 완료 표식이나 H0는 최신 개인정보 상태나 복원 공개를 승인하지 않는다. 복원 시에는 기존 독립 저널·최신 live 기준 H1을 대조하고 S 이후의 삭제·동의 철회·인증 폐기를 모두 재적용하며 격리를 유지한다.

## 미디어와 실행 환경의 보호

- 같은 S에서 URL·JSON 미디어 필드 17개를 검사한다. 실제 살아 있는 URL이 가리키는 파일 누락은 차단한다. `jobs.image_keys`의 누적 이력만 같은 사용자·같은 S의 완료된 파기 기록으로 삭제가 입증되면 예외로 세며, 키 원문은 출력하지 않는다. 새 미디어 필드나 모호한 파기 기록은 실패로 처리한다.
- 운영 경로는 정확한 버전 조건을 제공하는 GCS만 지원한다. 일반 S3 ETag 경로는 명시적으로 허용한 소유 loopback 시험에서만 사용한다. 권한·키·버킷 versioning을 추가하거나 넓히지 않았다.
- 현재 짧은 목록 경계는 단일 완전 페이지, 최대 1,000개 객체·2 MiB다. 잘린 목록을 성공으로 처리하지 않는다. 이 한도를 넘거나 기준 시점에 계속 작업이 활성인 경우에는 서비스 중단 대신 백업 실패·기존 경보로 표시한다.
- API·워커의 컨테이너 ID·이미지·PID·시작 시각을 고정하고 게시 직전·직후와 종료 시 다시 대조한다. 중간 재시작 후 `Running=true`가 된 경우를 무중단 성공으로 표시하지 않는다.
- 기존 배포·복구와 같은 호스트 백업 잠금을 사용한다. 복구 표식이 있으면 온라인 백업도 거절하며, 실패 시 서비스 종료·재시작 표식을 새로 만들지 않는다.

## 실행과 검증

예약 명령에는 `--capture-mode online`을 명시한다. 새 유효 서비스 검사기는 기본적으로 이 모드를 요구하며 누락·중복·모호한 모드를 거부한다. 오프라인 롤백 검증에는 `--expected-capture-mode offline`을 명시한다. 실제 설치 소스·pin과 현재 운영 검증 결과는 [운영 런북](OPERATIONS_TEST_RUNBOOK.md)과 [출시 현황](LAUNCH_STATUS.md)을 기준으로 한다.

```bash
python scripts/run_online_backup_fixture.py --report-dir /tmp/storybook-online-backup-report
```

시험은 소유한 loopback PostgreSQL 16·MinIO·Redis와 복사된 API·Celery, 가상 데이터만 사용한다. TLS 검증을 유지하고 실제 dump를 복원한다. 원격 게시 전송은 시험 대역이며 운영 GCS와의 서명·세대 조건 확인은 별도다. 프로젝트의 `.env`나 기존 볼륨을 불러오지 않는다. PostgreSQL 16의 `psql`, `pg_dump`, `pg_restore` 세 도구를 검증해 선택하며 CI는 공식 PostgreSQL 16 도구·이미지를 준비한다.

최종 두 단계 격리 검증에서는 기준 시점 29ms·전체 776ms 동안 SQL 쓰기 23회·실제 API 쓰기 23회·읽기 23회가 오류 없이 완료됐다. 원래 서비스 PID와 중지·재시작 0회를 확인했다. 잠금 해제와 전체 검증 사이에 live URL·새 개인정보 이력·일반 데이터를 바꿔도 S2의 원래 데이터만 검증하고 캡처했다. 실제 dump 복원과 최신 H1 사건 재적용 후에는 삭제된 책이 없어지고 계정 삭제 상태가 유지됐다. 12개 장애 시나리오를 통과했고, 후단 검증 실패 시 dump·원격 업로드 0회도 계수했다. 콜백 정지 시 504ms, 백업 프로세스 SIGSTOP 시에는 DB 자체 제한으로 1,002ms 후 쓰기가 재개됐다. 이는 운영 환경의 지연·성능·공개 승인을 대신하지 않는다. [최종 격리 검증](acceptance/2026-11-12-online-backup-fixture-two-phase/verification.json)

기존 실패 감지·예약 누락 감지·신호 누락 40분 경보는 유지한다. 과거 정상 백업을 이번 성공으로 바꾸거나 준비 상태를 캐시해 중단을 숨기지 않는다. 다음 자연 예약 실행은 별도의 실제 관측 대상이다.

## 2026-11-12 운영 적용 결과

운영 고정 소스는 `c37556444c2c679b909b0e1cedc50bef1ee7ac724c9c65c1aa8096ea404b14cd`의 218개 파일이다. 5개 서비스의 online 모드·엄격한 소스 검사·bytecode 0개를 확인했고 API·워커 이미지는 유지했다. 정규 백업 두 번이 각각 원격 미디어 67개 체크섬을 검증했다. 쓰기 경계는 1,410ms와 1,416ms였으며, 두 번째 실행의 공개 책 GET 37회와 설정 PATCH·저장 확인·원래 값 복원이 모두 성공했다. 컨테이너 ID·PID·시작 시각은 같았고 앱 중지·재시작은 없었다. [실제 동시 이용](acceptance/2026-11-12-online-backup-rollout/regular-online-backup-concurrent-api-v3.json)

첫 세트의 앞선 DB-only 검사에 이어 현재 소스의 네트워크 차단 PG16·MinIO에 DB와 미디어 67개 전체를 복원했다. 내용·메타데이터·비공개 접근과 H0 58건을 확인하고, 실제 원본·두 미러의 새 H1을 검사 전후 대조했다. H0=H1이며 신규 사건·신규 재적용은 0건이고 기존 체크포인트 효과를 확인했다. 운영 원본·미디어에는 쓰지 않았다. 이 결과는 원본 DB를 조회할 수 있는 조건의 격리 검사이며 독립 전역 최신성이나 운영 전환 승인이 아니다. [실제 전체 복원 범위](ACTUAL_BACKUP_RESTORE_2026-11-12.md)

정규 checker와 publisher가 통과했고 Cloud Monitoring에서 검증 완료 후의 새 정상 지표 1 및 활성화된 2,400초 신호 부재 경보를 확인했다. 한정된 실제 실행의 증거이며 다음 자연 예약 실행·재해 복구 시간·24시간 SLA를 대신하지 않는다. [클라우드 수신 확인](acceptance/2026-11-12-online-backup-rollout/cloud-monitoring-after-online-backup.json)
