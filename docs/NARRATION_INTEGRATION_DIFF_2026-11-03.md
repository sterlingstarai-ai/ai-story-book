# 낭독·개인정보 변경의 후보 이미지 통합 상태

2026-11-03 로컬 격리 작업 기록이다. 아래 후보는 실제 배포 승인이 아니며, 운영 DB·VM·이미지를 교체하지 않았다. 이미지 기반 `asb-privacy-pilot:20261102`의 애플리케이션 소스 해시는 운영 실행 컨테이너와 같았지만 이미지 ID는 운영 API·worker와 다르다.

## 이미 검증한 로컬 후보

- 음성·동의·삭제 처리 후보는 Google 음성 두 종류와 세 스타일, 동의 `purge_incomplete` 응답, 불완전한 S3 삭제 응답의 실패 처리 및 큐 예외 비노출을 포함한다. API 이미지에서 동의·S3 삭제 관련 테스트 17개, 양쪽 이미지에서 오프라인 합성 요청과 실패 주입이 통과했다. 이는 실제 Google 또는 S3 연결·음성 품질·실기기 검증이 아니다.
- 개인정보 witness 코드 후보는 위 항목에 witness 설정, 이중 기록, checkpoint·키·원본 펜스 및 관련 검증 코드를 추가한다. 이미지 내부의 관련 집중 테스트 66개와 임시 PostgreSQL 마이그레이션·commit 직전 SIGKILL 롤백이 통과했다. 코드를 이미지에 넣는 것만으로 이중 저장소가 구성되거나 최신 기록의 독립 보존이 보장되는 것은 아니다.
- 이 후보가 기본으로 승계한 `library.py`와 `characters.py`는 검토 시점 현재 소스와 해시가 같아 각각 책·캐릭터 삭제 이벤트 경로를 포함한다. 이후 수정이 들어오면 다시 비교해야 한다.

## 아직 후보에 포함되지 않은 변경과 의미

| 변경 | 포함하지 않았을 때의 제한 |
|---|---|
| 파기 큐 health 모듈과 호스트 검사기·타이머·알림 템플릿 | 오래된 파기 작업을 새 이진 health 신호로 감시하지 못한다. 모듈이 이미지에 있더라도 호스트 서비스와 알림 채널 설치·실제 신호 확인은 별도다. |
| 책 삭제 확인 영수증의 DB 모델, migration, 저널과 API 연계 | 새 확인 영수증을 저장·반환·복원하지 못한다. 삭제 이벤트 기록 자체와 영수증은 별도 기능이다. |
| 최신 TTS 입력 정리 | 새로 합성하는 음성에서 명백한 페이지·장면 안내를 제거하는 변경이 적용되지 않는다. 기존 저장 음원은 변경 후에도 자동 재생성되지 않는다. |
| `account_recovery.py` SQLite 트랜잭션 보완 | 로컬 SQLite의 특정 최초 등록 롤백 문제가 남는다. 변경 내용상 PostgreSQL 분기는 기존 경로다. |
| 이야기·그림 프롬프트와 LLM mock 문구 변경 | 해당 최신 콘텐츠 지시·mock 문구가 적용되지 않는다. 품질은 별도 실생성 및 사람의 검토가 필요하다. |

모델·저널·라우터·migration을 개별 파일만 혼합하지 않는다. 영수증 변경은 기존 낭독 migration `5de7a40b6c12 → 9c1e3a7f620d → 7e28d9a6b451` 뒤에 `8a34e19c6b72`를 추가한다. 로컬 배포 펜스를 세 단계로 갱신하고, 기존 후보에 현재 migration 스냅샷을 읽기 전용 마운트한 합성 PostgreSQL에서 커밋 및 커밋 전 SIGKILL 롤백을 확인했다. 새 영수증 모델·저널·라우터까지 하나로 묶은 최종 후보에서는 되돌림 방지와 관련 호출부를 다시 검증해야 한다.

후보 빌더는 검토된 각 파일과 파기 감시 호스트 템플릿의 SHA를 고정한다. 빌드 중 다른 작업이 파일을 바꾸면 성공 보고서를 내지 않고 중단한다. 최신 영수증과 TTS 변경이 끝난 뒤 새 매니페스트를 만들고 API·worker 양쪽의 전체 소스 차이, 동의·파기 실패 주입, witness 테스트, 세 단계 migration과 강제 종료 복구를 다시 확인한다. 격리된 PostgreSQL·MinIO로 DB와 매체를 옮기고 데이터 fingerprint를 재검사하는 운영 준비 코드도 추가했으나 아직 실행·검증하지 않았다. 독립 개인정보 원장의 최신성, 원장 재적용, VM 재부팅, 실제 제공자 권한·비용, 기기 검증이 남아 있으므로 운영 경로는 차단 상태다.

계정 범위 기능을 운영에서 사용하려면 별도 scope 키와 암호화 봉투, 키 지문을 각각 안전하게 보관하고 실제 복구를 선행해야 한다. 키를 만들거나 서버에 설치하지 않았다. 키가 없을 때 엔드포인트가 안전하게 실패하는 것과 서비스가 정상 동작한다는 것은 별개다.
