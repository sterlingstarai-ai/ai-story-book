## R1 — `USE_CELERY=true`인데 장기 작업 3종이 API in-process 실행

### 증상
`.delay()` 호출부가 책 생성·시리즈 2곳뿐이라, 페이지 재생성·인페인트·오디오는
`USE_CELERY` 분기 **없이** 항상 `background_tasks.add_task`로 API 프로세스에서 돌았다.
`tasks.py`의 `regenerate_page_task`는 시그니처가 현행 러너와 어긋난 채 아무도 호출하지
않는 죽은 코드였고, 인페인트·오디오는 태스크 자체가 없었다.

### 수정
**러너 정본을 서비스 계층으로 이동** (라우터에 두면 `tasks.py` → `routers` 순환):
- `apps/api/src/services/job_runners.py` **(신규)**
  - `set_regen_job_status` / `run_regeneration_job` / `run_inpaint_job` /
    `run_audio_job` / `generate_audio_pages` — books.py에서 그대로 이동
  - 인자는 전부 원시 타입이라 Celery 직렬화 가능(ORM 객체 미전달)

**Celery 태스크** (`apps/api/src/services/tasks.py`)
- `_run_tracked_job_async` (신규 공통 골격) — 재전달 멱등 가드 + 러너 실행을
  **하나의 코루틴**으로 묶어 태스크당 `run_async` 1회 (C1 규약 준수)
- `regenerate_page_task` **재작성** — 시그니처를 러너와 1:1로 정렬
  (`regen_job_id, original_job_id, book_id, page_number, mode, feedback`)
- `inpaint_page_task` **신규**
- `generate_audio_task` **신규** (`time_limit=420` — 러너 내부 300초 타임아웃보다 넉넉히)
- 전부 `acks_late=True · reject_on_worker_lost=True · max_retries=2` 유지

**라우터 분기** (`apps/api/src/routers/books.py`)
- `_dispatch_long_running_job` 헬퍼 신설 (books.py:333~) — `settings.use_celery`면
  `.delay()`, 아니면 `background_tasks.add_task(runner, …)`. **두 경로가 같은 함수 실행**
- 적용: 재생성(books.py:762), 인페인트(books.py:880), 오디오(books.py:1339)
- 선행 로직(멱등성·소유권·크레딧)은 미변경 — 분기만 추가

> **스코프 초과 1건(보고 후 승인 필요)**: enqueue 실패 시 잡을 `queued`로 방치하면

> 즉시 failed 전이시키는 fail-closed 처리를 넣었다(create_book의 기존 계약과 동일).
> "분기만 추가" 지시를 넘어선 유일한 지점이다.
