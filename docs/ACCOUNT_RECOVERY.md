# 계정 복구와 기기 인증

작성: 2026-09-06. 무료 제한 베타에 적용되는 구현과 운영 기준이다.

기기를 바꾸거나 앱을 다시 설치하기 전에 보호자 설정에서 **복구 코드**를 발급해 별도로 보관하면 기존 서재, 자녀 프로필, 설정, 동의 기록을 되찾을 수 있다. 복구는 새 계정을 기존 계정과 합치는 기능이 아니다. 복구한 계정으로 전환하며 이전 기기의 인증은 폐기된다. 새 기기에서 이미 만든 책은 자동으로 합쳐지지 않는다.

## 보호자 사용 흐름

1. 보호자 영역에서 복구 코드를 발급하고 비밀번호 관리자 등 기기 외부의 안전한 장소에 보관한다. 현재 기기는 계속 사용할 수 있다.
2. 새 기기의 시작 화면 또는 보호자 계정 복구 화면에 코드를 입력한다.
3. 복구가 완료되면 기존 서재와 서버의 동의 상태를 불러온다. 동의가 철회되었거나 필요한 동의가 없으면 동의 흐름을 다시 따른다.
4. 새 복구 코드가 표시된다. 이전 코드는 다른 기기를 복구하는 데 사용할 수 없으므로 새 코드를 보관한다.

복구 코드는 비밀번호처럼 취급한다. 코드를 가진 사람은 계정에 접근할 수 있다. 이 기능은 이름·이메일·전화번호를 수집하거나 외부 로그인 서비스에 의존하지 않는다. 기기 인증과 복구 코드를 모두 잃은 경우 운영자가 본인임을 확인할 수 있는 수단은 없으며 임의로 서재를 넘겨주지 않는다.

## API 계약

모든 응답에는 `Cache-Control: private, no-store`가 적용된다. 복구 코드와 새 기기 인증은 URL에 넣지 않는다.

| 요청 | 인증 | 응답 또는 동작 |
|---|---|---|
| `GET /v1/account/session` | `X-User-Key` | `{status: "active"}`. 소유권 식별자를 응답하지 않음 |
| `GET /v1/account/recovery` | `X-User-Key` | `{enabled, recovery_code_created_at}` |
| `POST /v1/account/recovery-code` | `X-User-Key` | `{recovery_code, created_at}`. 새 코드 발급 또는 기존 코드 교체 |
| `POST /v1/account/recover` | 복구 코드 자체 | 본문 `{recovery_code, new_user_key}`. `{status: "recovered", recovery_code, created_at}` 반환 |

- 복구 코드는 `ASB-R1-` 뒤에 암호학적으로 안전한 난수 32바이트를 URL-safe Base64로 인코딩한 43자다.
- 새 기기 인증은 `asb_device_` 뒤에 같은 방식으로 만든 43자다. 클라이언트는 이 값을 요청 **전에** 보안 저장소의 보류 영역에 저장하고 읽어 확인한다.
- 최초 복구 성공은 새 복구 코드를 반환한다. 동일한 이전 복구 코드와 **동일한 새 기기 인증**으로 재시도하면 이미 완료된 복구를 확인하고 `recovery_code: null`을 반환할 수 있다. 이후 새 기기 인증으로 `/recovery-code`를 호출해 표시할 새 코드를 발급한다.
- 이미 사용한 코드로 **다른 기기 인증**을 설치하려는 요청은 `401 RECOVERY_CODE_INVALID`다. 폐기·미등록 기기 인증은 `401 UNAUTHORIZED`다.
- 익명 복구 요청은 서버가 확인한 연결 주소당 10분에 10회로 제한한다. Redis에 접근하지 못하면 `503 SERVICE_UNAVAILABLE`로 복구를 중단한다. 신뢰하는 프록시 설정이 없으면 프록시 주소가 하나의 제한 단위로 묶일 수 있다. 앱 서버의 trusted-proxy 설정과 실제 외부 주소 전달을 배포 전 확인해야 한다.

## 응답 유실과 저장소 오류

복구가 서버에서 완료되었는데 응답을 받지 못하면 이전 기기 인증과 이전 복구 코드는 이미 폐기되었을 수 있다. 이 때문에 서버에서 새 기기 인증을 만들어 응답하는 방식 대신, 클라이언트가 먼저 만든 인증을 보류 저장소에 보관한다.

클라이언트는 보류 인증으로 `/session`을 확인하고 성공하면 해당 인증으로 전환한다. 조회가 `401`이어도 이전 요청이 아직 처리 중일 수 있으므로 네트워크 오류 뒤의 보류 인증을 즉시 버리지 않는다. 재시도에는 **같은 보류 인증**을 사용한다. 복구된 인증을 보안 저장소에서 다시 읽어 확인하기 전에는 보류 인증을 삭제하지 않는다.

코드 발급 응답만 유실된 경우 현재 기기의 인증은 여전히 유효하다. 다시 발급하면 된다. 보안 저장소 기록 실패·서버 연결 실패를 빈 서재의 새 계정으로 조용히 바꾸지 않는다.

## 서버가 보존하는 상태

`account_identities`는 기존 데이터의 `user_key`를 소유권 식별자로 유지하고 기기 인증과 복구 코드의 SHA-256 해시를 별도로 저장한다. 두 종류의 해시는 서로 다른 도메인 문자열로 구분한다. 복구 코드는 충분한 난수로 생성하므로 사람이 정한 비밀번호용의 느린 해시 대신 조회 가능한 해시를 사용한다.

기존 UUID 계정은 명시적으로 복구 코드를 발급하기 전까지 기존 방식으로 동작한다. 등록된 계정의 소유권 UUID는 복구 후 인증으로 다시 사용할 수 없다. 새 형식의 기기 인증이 조회되지 않으면 새 계정으로 해석하지 않는다. 선택적 인증을 사용하는 오늘의 동화 조회에도 같은 규칙을 적용한다.

복구는 PostgreSQL 행 잠금과 조건부 갱신으로 기기 인증·복구 코드 교체를 함께 커밋한다. 두 기기가 같은 코드를 동시에 사용해도 한 기기만 성공한다. 이미 인증된 이전 요청이 복구 이후 코드를 교체하거나 계정을 삭제하지 못하도록 해당 변경의 커밋 전 현재 기기 인증을 다시 비교한다. 일반적인 읽기·쓰기 요청은 요청 시작 시 인증하며 이미 승인되어 진행 중인 요청 전체를 소급 취소하는 기능은 아니다.

API 응답, 검증 오류, 애플리케이션 로그에 복구 코드·기기 인증을 남기지 않는다. 일반 요청 제한의 Redis 키도 인증 원문 대신 해시를 사용한다. 서버에는 원문 복구 코드를 재조회하는 기능이 없다.

계정 전체 삭제는 데이터 삭제와 같은 트랜잭션에서 활성 기기 인증, 복구 코드, 재시도 해시를 제거하고 폐기 표식을 남긴다. 이 최소 표식은 이전 소유권 UUID로 인증을 우회하는 것을 막는다. 저장소 파기가 지연되면 기존 durable outbox가 재시도한다. 삭제 성공 또는 파기 대기 응답을 받은 앱은 새 기기 인증을 만들어 초기 동의 화면으로 이동한다. 복구를 등록하지 않은 기존 계정의 삭제 동작은 유지된다.

## 배포·백업·유료 전환 조건

- API를 올리기 전에 Alembic `c4d5e6f7a8b9`까지 적용한다. 이 변경은 기존 소유권 행을 옮기지 않는 테이블 추가다.
- 등록된 계정이 존재하면 이 마이그레이션의 자동 downgrade를 차단한다. 테이블 제거 또는 복구 기능 이전 API로 롤백하면 폐기된 UUID가 다시 인증될 수 있다.
- 과거 데이터베이스 백업을 복원하면 당시의 기기 인증·복구 코드도 살아날 수 있다. 외부 트래픽을 막은 상태에서 최신 인증 폐기 상태 및 백업 이후 삭제·동의 철회 기록을 재적용한 뒤 공개한다. 최신 폐기 상태를 확보할 수 없으면 기존 인증을 안전하다고 간주하지 않는다. 운영자가 임의의 계정에 새 복구 코드를 발급하는 우회 경로는 만들지 않는다.
- 복구는 계정 소유권을 유지하므로 기존 구매·크레딧 기록을 다른 계정으로 이전하지 않는다. 새 기기 인증은 스토어의 안정적인 `appAccountToken`이 아니다. 유료 신규 구매는 별도의 안정적인 결제 계정 식별자와 실제 영수증·환불·복원 검증을 완료하기 전까지 비활성 상태를 유지한다.
- 보관·폐기 정책과 법무 검토는 별도 출시 요건이다. 이 구현은 기존 개인정보 동의 문구를 변경하지 않는다.

## 검증 근거

`apps/api/tests/test_account_recovery.py`에서 실제 HTTP 경계의 소유권 유지, 폐기된 기기와 원래 UUID 차단, 코드 교체, 정확한 재시도, 다른 계정 인증 충돌, 동의 유지·철회, 계정 삭제, 서버 연결 실패, 요청 제한, 비밀값 비노출을 검증한다.

`apps/api/tests/test_account_recovery_pg.py`는 `E2E_PG_DATABASE_URL`이 있을 때 실제 PostgreSQL에 마이그레이션을 적용하고 서로 다른 세션에서 동시 복구·같은 기기 재시도·코드 교체 경쟁·삭제 경쟁을 검증한다. 설정이 없으면 명시적으로 생략되며 SQLite 통과를 PostgreSQL 검증으로 간주하지 않는다. 2026-09-06 로컬 PostgreSQL 15의 실제 실행에서 4개 모두 통과했다.
