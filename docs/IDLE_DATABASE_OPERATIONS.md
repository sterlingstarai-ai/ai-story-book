# 유휴 데이터베이스와 운영 점검

2026-11-11 후보. 운영 적용과 실제 유휴 중단·재연결 증거는 적용 후 이 문서에 추가한다.

Neon Free는 프로젝트당 월 100 CU시간이며 5분 유휴 후 compute를 중단한다. 최소 0.25 CU를 계속 실행하면 30일에 180 CU시간이므로 무료 한도를 넘는다. 프로젝트의 모든 compute 사용량이 합산된다. 이는 사용량 계산이며 실제 청구액이나 이번 달 잔여량의 예측이 아니다. [공식 한도와 계산](https://neon.com/docs/introduction/plans)

서버 프로세스와 DB 의존성은 다른 주기로 점검한다.

| 점검 | 주기 | 의미 |
| --- | --- | --- |
| HTTPS `/health/live` 신호 | 5분 | API 프로세스 응답. DB·AI·저장소 준비 상태를 대신하지 않는다. |
| HTTPS `/health/ready` 신호 | 매시 00·30분 | 실제 현재 DB·Redis·저장소·제공자 상태. 마지막 정상 값을 재사용하지 않는다. |
| 개인정보 파기 큐 신호 | 매시 00·30분 | 독립 읽기 전용 검사. 신호 누락 경보는 45분이다. |
| API 작업·개인정보 재시도 | 대기 작업·오류가 있으면 5분 | 기존 정리·환불·기록 게시 작업을 독립 실행한다. |
| 대기 작업이 없는 API 유지보수 | 매시 00·30분 또는 요청 커밋 후 | 커밋 뒤 메모리 내 신호로 깨운다. 신호에는 사용자·요청 데이터가 없다. |
| 월간 크레딧 점검 | 매시 정각 | 세션을 닫은 뒤 대기한다. 결제 확인·원자적 지급·멱등성은 그대로다. |

알려진 작업이 없다고 확인한 경우에만 길게 대기한다. `queued/running` 작업, 미완료 파기 지시, 미승인 사진의 만료·생성 처리, 미게시 개인정보 기록은 빠른 점검을 유지한다. 점검 자체가 실패해도 5분 주기로 재시도한다. 요청 세션만 커밋 알림을 보내므로 유지보수 자신의 커밋이 무한 재실행을 만들지 않는다. 롤백은 알림을 보내지 않는다.

알림은 현재 단일 API 프로세스의 깨우기 신호이며 영속 작업 큐를 대신하지 않는다. 프로세스 재시작 시 즉시 실제 DB를 스캔하고, 유휴 중 외부에서 직접 추가된 작업도 다음 30분 점검에 발견한다. 여러 API 복제본의 분산 깨우기나 DB 직접 쓰기의 5분 발견 시간을 입증한 것은 아니다.

경보의 정렬 구간도 표본 주기에 맞춘다. 전체 준비·파기 신호는 30분 정렬에서 관측한 실패 하나로 경보를 만들고 45분 누락을 별도 감지한다. 프로세스 신호는 별도 지표와 정책을 사용한다. 의존성 장애의 자동 발견은 기존 5분 점검보다 늦어질 수 있다. 수동·실제 사용자 요청의 `/health/ready` 의미는 바뀌지 않는다. [Google Cloud의 정렬·재검사 설명](https://docs.cloud.google.com/monitoring/alerts/concepts-indepth)

요청이 계속되거나 작업·삭제 오류가 남으면 DB가 계속 실행될 수 있다. 이 최적화는 무료 한도 보장이나 24시간 무중단 약속이 아니다. 요금제·compute 크기·제공자 유효기간·생성 비용 한도는 변경하지 않는다.

배포 때는 정확한 API·워커 이미지와 백업 소스 사본을 함께 고정한다. 기존 경보의 수신 채널을 보존한 채 주기를 먼저 맞추고, 새 지표가 수신되는지 확인한다. 이전 unit·경보 구성은 비공개 보존하고 실패 시 복구한다. 재시작·백업 중에는 공유 복구 잠금과 표식을 그대로 유지한다.

코드 검사는 유휴/대기 큐, 요청 커밋/롤백, 백그라운드 커밋의 자기 깨우기 방지, 알림 전후 경쟁, 다른 스레드의 알림, HTTP 두 단계의 혼동 방지, 서로 다른 지표 이름을 포함한다. 실제 compute 중단과 공개 주소의 재연결 성공은 별도 운영 증거가 필요하다.
