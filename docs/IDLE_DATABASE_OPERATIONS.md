# 유휴 데이터베이스와 운영 점검

2026-11-11 운영 API·워커와 점검 주기에 적용했고 실제 유휴 중단 후 기존 책의 첫 요청 재개를 확인했다.

Neon Free는 프로젝트당 월 100 CU시간이며 5분 유휴 후 compute를 중단한다. 최소 0.25 CU를 계속 실행하면 30일에 180 CU시간이므로 무료 한도를 넘는다. 프로젝트의 모든 compute 사용량이 합산된다. 이는 사용량 계산이며 실제 청구액이나 이번 달 잔여량의 예측이 아니다. [공식 한도와 계산](https://neon.com/docs/introduction/plans)

서버 프로세스와 DB 의존성은 다른 주기로 점검한다.

| 점검 | 주기 | 의미 |
| --- | --- | --- |
| HTTPS `/health/live` 신호 | 5분 | API 프로세스 응답. DB·AI·저장소 준비 상태를 대신하지 않는다. |
| HTTPS `/health/ready` 신호 | 매시 00·30분 | 실제 현재 DB·Redis·저장소·제공자 상태. 마지막 정상 값을 재사용하지 않는다. |
| 개인정보 파기 큐 신호 | 매시 00·30분 | 독립 읽기 전용 검사. 신호 누락 경보는 45분이다. |
| API 작업·개인정보 재시도 | 대기 작업·오류가 있으면 5분 | 기존 정리·환불·기록 게시 작업을 독립 실행한다. |
| 대기 작업이 없는 API 유지보수 | 매시 00·30분 또는 요청 커밋 후 | 커밋 뒤 메모리 내 신호로 깨운다. 신호에는 사용자·요청 데이터가 없다. |
| 월간 크레딧 점검 | 매시 정각 | 세션을 닫은 뒤 대기한다. 결제 확인·원자적 지급·멱등성은 그대로다. |

알려진 작업이 없다고 확인한 경우에만 길게 대기한다. `queued/running` 작업, 미완료 파기 지시, 미승인 사진의 만료·생성 처리, 미게시 개인정보 기록은 빠른 점검을 유지한다. 점검 자체가 실패해도 5분 주기로 재시도한다. 요청 세션만 커밋 알림을 보내므로 유지보수 자신의 커밋이 무한 재실행을 만들지 않는다. 롤백은 알림을 보내지 않는다.

알림은 현재 단일 API 프로세스의 깨우기 신호이며 영속 작업 큐를 대신하지 않는다. 프로세스 재시작 시 즉시 실제 DB를 스캔하고, 유휴 중 외부에서 직접 추가된 작업도 다음 30분 점검에 발견한다. 여러 API 복제본의 분산 깨우기나 DB 직접 쓰기의 5분 발견 시간을 입증한 것은 아니다.

경보의 정렬 구간도 표본 주기에 맞춘다. 전체 준비·파기 신호는 30분 정렬에서 가장 최근에 관측한 값을 사용해 실패 시 경보를 만들고 45분 누락을 별도 감지한다. 프로세스 신호는 별도 지표와 정책을 사용한다. 의존성 장애의 자동 발견은 기존 5분 점검보다 늦어질 수 있다. 수동·실제 사용자 요청의 `/health/ready` 의미는 바뀌지 않는다. [Google Cloud의 정렬·재검사 설명](https://docs.cloud.google.com/monitoring/alerts/concepts-indepth)

요청이 계속되거나 작업·삭제 오류가 남으면 DB가 계속 실행될 수 있다. 이 최적화는 무료 한도 보장이나 24시간 무중단 약속이 아니다. 요금제·compute 크기·제공자 유효기간·생성 비용 한도는 변경하지 않는다.

배포 때는 정확한 API·워커 이미지와 백업 소스 사본을 함께 고정한다. 기존 경보의 수신 채널을 보존한 채 주기를 먼저 맞추고, 새 지표가 수신되는지 확인한다. 이전 unit·경보 구성은 비공개 보존하고 실패 시 복구한다. 재시작·백업 중에는 공유 복구 잠금과 표식을 그대로 유지한다.

코드 검사는 유휴/대기 큐, 요청 커밋/롤백, 백그라운드 커밋의 자기 깨우기 방지, 알림 전후 경쟁, 다른 스레드의 알림, HTTP 두 단계의 혼동 방지, 서로 다른 지표 이름을 포함한다. 실제 compute 중단과 공개 주소의 재연결 성공은 아래 운영 증거로 구분한다.

## 적용한 버전과 검증 범위

- API `sha256:4c9ca477f3706b76b8d14a6bd79e3f264661ebb08605e1c2b297c67cd7b81ad8`, 워커 `sha256:07bdb455d6a74ce716da7c7f76a2d81530e38f981ea0e1b0c8d0a2baabbde9d6`. 실행 중인 두 컨테이너의 소스 142개가 독립 매니페스트 `2be4f9f30f1b50e6cc1b16e5846874cdfbc77c96817eb617dc086555964c53ec`와 일치했다. 기본 Flare·선택 Sunburst 교정도 양쪽에서 확인했다.
- 외부 공개 준비 상태 200 영수증 후 전환을 확정했다. 현재 API 이미지의 백업 소스 사본, 원본 이미지·설정 복구 경로, systemd 복구 실행 명령을 보존했다. [실행 소스와 백업 연결](acceptance/2026-11-11-backend-idle-r8/runtime-and-backup-binding-audit.json)

Google의 무료 표준 디스크 제공량은 **계정 전체** 30GB-월이므로 이 프로젝트 외 사용량을 포함한 실제 청구액 0원을 확인했다는 뜻은 아니다. [용량·온라인 확장](acceptance/2026-11-11-backend-idle-r8/grow-and-image-build.log) · [무료 제공 기준](https://docs.cloud.google.com/free/docs/free-cloud-features)
- 고정 의존성 환경의 API 전체 3,517개 통과·32개 건너뜀, 추가 유지보수 47개와 신호 8개가 통과했다. 운영과 같은 FastAPI 0.162.0·Starlette 1.10.0으로 OpenAPI를 생성했을 때 기존 계약과 같았다. 기존 로컬 venv는 수정하지 않았다. CI나 최신 물리 기기 검증을 새로 완료했다는 뜻은 아니다.

현재 일일 백업은 여전히 서비스 중지 구간이 있다. 이 변경은 그 중단을 제거한 온라인 백업이 아니다. 별도 콜드 복구 첫 성공 시험은 이전 r7 앱 이미지에서 수행했으며, 최신 r8 조합의 실제 OS 재부팅 시험으로 혼동하지 않는다.

## 실제 유휴 중단과 첫 요청 재개

대기 유지보수 작업과 열린 유휴 트랜잭션이 0인 것을 확인한 뒤 DB 요청을 보내지 않았다. 6분 30초의 최소 대기 뒤 Neon의 인증된 Computes 화면에서 같은 기본 endpoint가 `SUSPENDED`인 것을 직접 확인했다. 그 상태를 저장한 뒤 기존 가상 책의 상세 요청 한 번만 보냈고, HTTP 재시도 없이 200을 받았다. 응답은 15.862초였고 Postgres 시작 시각도 그 요청 뒤로 바뀌었다. 콘솔에서 `ACTIVE` 재개를 확인했다.

책의 12쪽 구성, 표지와 마지막 삽화, 마지막 쪽의 기존 30.65초 WAV 및 캐시 바이트 일치와 최종 준비 상태 200을 확인했다. 새 동화·음원·실제 아동 데이터는 사용하지 않았다. 이 시험은 새 Flare 책 생성이나 실기기 전체 낭독 검사가 아니다. [결과](acceptance/2026-11-11-idle-db-resume/result.json) · [유휴 화면](acceptance/2026-11-11-idle-db-resume/neon-suspended.png) · [재개 화면](acceptance/2026-11-11-idle-db-resume/neon-resumed.png)

콜드 재개가 기존 10초 점검 창보다 길 수 있음을 실측했으므로 준비 상태 HTTP 점검만 30초로 제한하고 systemd 명령은 90초로 맞췄다. 생존 점검은 10초를 유지한다. 성공에는 여전히 실제 200과 정상 본문·제공자 상태가 필요하며, 오류를 정상으로 바꾸지 않는다. 후속 고정 패키지 `2d5d8f4f5cfd325636aa022364a6ffd5d7aef83858207866c9c620d247310ae1`의 11개 파일을 검증해 두 신호 실행 경로를 전환했다. API·워커와 타이머/경보 주기는 다시 바꾸지 않았다. 실제 준비 신호 1 게시를 확인했다. [예산 보정과 실제 신호](acceptance/2026-11-11-idle-db-candidate/bounded-probe-update.json)

한 번의 유휴 재개 결과이며 상시 지연 시간 보장이 아니다. 무료 DB가 다시 잠든 뒤 첫 접속에서는 대기 시간이 생긴다. 기존 책의 기기 캐시·앱 화면 반응은 최종 실기기 검사에서 따로 확인한다.
