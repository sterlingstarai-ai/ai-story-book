## 2026-11-03 운영 이미지 추가 확인

비공개 VM의 실행 중 API·worker 이미지 ID는 v8 매니페스트에 기록된 운영 이미지 ID와 각각 일치한다. 두 실행 컨테이너의 `src`·`alembic` 소스 해시와 Python 버전 해시는 로컬 후보 기반과 같았지만, 설치된 Python 패키지 이름·버전 해시는 운영 두 컨테이너끼리만 같고 로컬 기반과는 달랐다. 소스와 Python 버전 일치만으로 후보를 운영과 동등하다고 판정하지 않는다. 임시 SSH 항목 정리의 확인 범위는 위 정정 사항을 따른다. [비밀 없는 관측 결과](acceptance/privacy-final-synthetic-2026-11-03/production-image-source-observation.json).

다음 단계는 운영과 동일한 정확한 이미지로 격리 후보를 재현하거나, 안전한 비공개 비교에서 패키지 이름·버전 차이를 식별해 재현한 다음 네이티브 라이브러리와 격리 실행까지 검증하는 것이다. 패키지 비교와 별개로 최신 개인정보 기록, 복원 및 재부팅 가드는 계속 미충족이며 배포는 승인되지 않았다.

패키지의 `Name`·`Version` 필드만 대조한 결과 차이는 한 건이었다. 운영 API·worker는 `cryptography 50.0.2`, 로컬 v8 기반과 현재 `apps/api/requirements.txt`는 `cryptography 50.0.1`이다. 나머지 패키지 이름과 버전은 일치한다. 이는 실제 바이너리·네이티브 라이브러리나 OS 구성이 일치한다는 뜻은 아니다. 운영 이미지 자체의 출처·민감정보를 검토한 뒤 그 정확한 기반으로 격리 재현하거나, cryptography 버전 및 잠금 변경의 영향을 검토·검증한 별도 후보가 필요하다. 현재 의존성 파일이나 운영 서비스를 변경하지 않았다.

읽기 전용 `docker diff`에서는 두 실행 컨테이너의 writable layer에 경로명 기준 cryptography 관련 변경이 각각 0건이었다. 실행 컨테이너의 `/app/requirements.txt`에서는 정확한 `cryptography==버전` 한 줄을 확인하지 못했으므로 운영 50.0.2의 설치 경로·시점은 미확인이다. 마운트나 이미지 생성 이력은 이 검사만으로 배제할 수 없다. 기존 배포 어댑터의 이미지 ID 및 환경·마운트 대조는 Python 패키지와 네이티브 바이너리의 독립적인 동등성 검사와 다르다. 운영 이미지의 민감정보·출처를 먼저 확인하고 정확한 운영 이미지로 격리 빌드한 다음 버전·바이너리·실행 회귀 검증을 수행해야 한다.

운영 이미지 표시 크기는 API 약 407 MB, worker 약 397 MB이며, 조사 당시 Mac 파일시스템의 여유 공간은 약 174 GiB였다. 내보낸 아카이브 크기와 빌드 중 복제·Docker Desktop 가상 디스크 여유는 별도 확인이 필요하다. 이미지 레이어에는 현재 파일 목록에서 사라진 사용자 데이터나 비밀이 남을 가능성을 배제하지 못했으므로 이미지는 전송·저장하지 않았다. 향후 레이어와 이미지 설정의 민감정보 위험을 안전하게 평가하고, 필요한 공간 및 전송 무결성을 검증한 뒤에만 제한된 격리 위치에서 다룬다.

[합성 결과](acceptance/2026-11-03-mirror-reconciliation/result.json). 이 변경은 아직 운영에 배포되지 않았으며 최신 기록 완전성을 입증하지 않는다.

추가 검증: API 전체 2,637개 통과·27개 건너뜀, Flutter 전체 701개 통과·2개 건너뜀 및 분석 통과. 이후 변경된 미러·백업 관련 집중 검사 40개, 낭독 배포 어댑터 관련 검사 27개가 통과했다. [낭독 v7 매니페스트](../infra/gcp-pilot/narration-receipt-candidate-v7-manifest.json)는 로컬 후보에 대한 고정값이며 운영 이미지와 동일성이나 배포 승인을 뜻하지 않는다.

체크포인트 검증은 현재 표식뿐 아니라 모든 이전 세대의 인증·사건 집합을 확인하도록 보완했다. 누락, 변조 및 시간 역행을 거부하며 연속 세대 수는 256개, 검증은 30초의 소프트 제한이다(단일 외부 저장소 호출을 강제 종료하지는 못한다). 집중 검사 19개 및 [네트워크 차단 합성 복원 시험](acceptance/2026-11-03-checkpoint-chain/offline-restore-1d324ea29e5dd9f7fb64d004a8ed626b.json)이 통과했다. 이후 소스 변경이 있어 v7은 최신 후보가 아니다. 외부 최신 기록 자체가 빠짐없이 존재한다는 증명은 여전히 없다.

기존 허구 그림 표본의 장면을 육안 확인했다. 일반 신발과 미사용 스케이트가 함께 있는 장면은 정상일 수 있지만, 스케이트를 신고 있으면서 동일 장비가 바닥에 다시 나타난 장면은 중복이다. 기존 `action_mismatch` 검수와 교정 지시에 명확한 중복만 감지하도록 추가했으며 관련 모의 검사 117개가 통과했다. 실제 새 그림에 대한 검출률과 품질은 확인하지 않았다.

체크포인트와 그림 검수 변경을 포함한 [v8 로컬 서버 후보](../infra/gcp-pilot/narration-receipt-candidate-v8-manifest.json)를 빌드했다. [소스 일치 결과](acceptance/privacy-final-synthetic-2026-11-03/candidate-v8-build.json)와 allowlist 검사 7개는 로컬 후보에 대한 것이며, 실제 운영 기반 이미지와의 동일성이나 배포 승인을 의미하지 않는다.

운영 컨테이너 읽기 전용 확인: API·worker 이미지 ID는 기존 매니페스트의 운영 기준과 일치했고 `/app/src`·`/app/alembic` 트리와 Python 버전, 설치 패키지 이름·버전을 비교했다. 운영과 로컬 후보 기반의 소스 및 Python 버전은 일치했으나 `cryptography`는 운영 50.0.2, 로컬 50.0.1이었다. 나머지 패키지 이름·버전은 같았다. 이 비교는 바이너리·OS·설정 동등성을 입증하지 않는다. 임시 SSH 항목 정리의 확인 범위는 위 정정 사항을 따른다.

실패한 개인정보 기록이 재시도 배치 전체를 막지 않도록 하고, DB에 순환 커서를 두어 첫 배치가 계속 실패하더라도 뒤의 기록을 시도하도록 보완했다. 마이그레이션 `4c2d8f71b906`은 기존 기록을 수정하지 않는다. 일회용 PostgreSQL에서 여러 worker 경합, 충돌·중단 후 재방문 및 안전한 downgrade 조건을 검증했다. [검증 결과](acceptance/2026-11-03-retry-fairness-final/result.json). 운영 미적용이며 독립적 최신 기록의 완전성을 증명하지는 않는다.

백업은 유휴 사전 점검을 추가해 작업이 있는 경우 API를 중단하기 전에 포기하도록 했다. 중단 직후 기존 점검도 유지해 경합을 차단한다. 성공하는 백업은 여전히 서비스 중단이 필요하다. [백업 후보](BACKUP_CANDIDATE_2026-11-03.md)는 별도로 고정·dry-run했으나 운영에 설치하지 않았다. 서버의 최신 로컬 후보는 [v9 매니페스트](../infra/gcp-pilot/narration-receipt-candidate-v9-manifest.json)이며 운영 이미지 동등성·배포 승인은 입증되지 않았다.

최종 후속: 서버 전체 테스트 2,666개 통과·27개 건너뜀, Flutter 전체 701개 통과·2개 건너뜀. 배포 준비 도구가 새 head `4c2d8f71b906`을 인식하도록 갱신했으며 집중 검사 15개와 일회용 PostgreSQL의 migration 커밋·강제 중단 롤백을 확인했다. [v10 리허설](acceptance/privacy-final-synthetic-2026-11-03/candidate-v10-migration-rehearsal.json), [v10 매니페스트](../infra/gcp-pilot/narration-receipt-candidate-v10-manifest.json). 운영에는 적용하지 않았고 공개·복원 승인도 아니다.

기록 기능 활성 시 세션에 기록기가 빠졌으면 보호 변경을 차단하고, 외부 기록 쓰기 후 암호문을 재조회해 확인한다. 집중 검사 45개 및 [합성 PostgreSQL·MinIO 리허설](acceptance/2026-11-03-privacy-readback/result.json)을 통과했다. 최신 로컬 서버 후보는 [v11](../infra/gcp-pilot/narration-receipt-candidate-v11-manifest.json), 백업 후보는 [v2](BACKUP_CANDIDATE_2026-11-03.md)이며 운영 설치·최신 기록 완전성은 여전히 미검증이다.

후속 검증: 서버 전체 2,671개 통과·27개 건너뜀. 이후 GCS 기록 목록의 손상된 빈 응답, 잘못된 형식·토큰, 중복 이름, 1,024페이지 초과를 거부하고 정상 빈 목록은 허용하도록 수정했다. 미결 intent와 손상 응답의 복원 차단을 포함해 집중 검사 27개가 통과했다. S3 백업 목록에도 10,000페이지 한도를 추가했으며 관련 검사 25개가 통과했다. 변경 후 v11과 백업 v2는 이전 후보이므로 새 후보 고정이 필요하다. 정상 형식이지만 실제 객체가 누락된 공급자 응답이나 기록의 최신성까지 증명하지는 못한다.

이후 변경을 반영한 [서버 후보 v12](../infra/gcp-pilot/narration-receipt-candidate-v12-manifest.json)와 [백업 후보 v3](BACKUP_CANDIDATE_2026-11-03.md)를 별도 생성했다. 이전 후보는 보존했다. 둘 다 로컬 후보이며 운영 설치 및 복원 승인은 아니다.

원본 상실 모의: 삭제 성공 응답 후 commit 게시만 실패시킨 합성 PostgreSQL을 제거했다. 외부 intent가 남으면 예전 증인 표식이 있어도 복원 준비가 차단됐다. intent까지 소실하면 예전 서명은 유효해도 최신성을 증명할 수 없고 복원 승인은 false다. [재현 결과](acceptance/2026-11-03-privacy-source-loss/result.json). 실제 운영 데이터는 사용하지 않았다.

백업 읽기 전용 프로토타입: 일회용 PostgreSQL 펜스 중 합성 HTTP GET을 허용하고 DELETE와 별도 DB 쓰기를 막는 시험은 통과했다. 그러나 같은 기간 별도 MinIO 객체 생성·삭제는 가능했다. [시험 결과](acceptance/2026-11-03-backup-readonly-prototype/result.json). 실제 앱의 모든 저장소 작성자와 진행 중 요청까지 막는 증거가 없으므로 무중단 운영 전환은 금지하고 기존 방식을 유지한다.

후속 공통 쓰기 잠금 시험에서 정상적인 협력 PUT/copy/delete는 차단됐지만, 실행 중 DB 세션이 끊기면 잠금이 풀려 백업의 배타 잠금 중에도 S3 copy가 완료되는 위험을 일회용 PostgreSQL·MinIO에서 재현했다. [시험 결과](acceptance/2026-11-03-storage-cooperative-fence/result.json). 운영에 연결하지 않았으며 durable in-flight 추적, 외부 작성자 권한과 장애 후 검증이 해결되기 전에는 무중단 전환을 승인하지 않는다.

추가 시험에서는 같은 DB 세션의 shared lock 아래 미완료 의도를 먼저 커밋했다. DB 연결 종료 후 S3 PUT이 늦게 완료돼도 남은 의도가 시험용 백업을 막고 동일 작업 재시도를 거부했다. [결과](acceptance/2026-11-03-storage-durable-intent-v2/result.json). 커밋 응답 유실은 예외 주입이며 실제 네트워크 단절 시험이 아니다. 실 앱·worker·scheduler 및 외부 작성자는 이 방식에 연결되지 않았다.

이후 시험 전용 [durable-intent 공통 모듈](../scripts/synthetic_storage_intent.py)로 리허설을 분리하고, 실제 일회용 PostgreSQL·MinIO에서 PUT 지연·DB 연결 상실·copy/delete 및 작업 ID 중복 거부를 다시 확인했다. [결과](acceptance/2026-11-03-synthetic-durable-module/result.json). 운영 코드·마이그레이션과 외부 작성자에는 연결되지 않았으므로 무중단 보장은 여전히 없다.

스토리지 삭제 목록의 잘린 페이지·잘못된 완료 상태를 거부하고, 객체를 삭제했다면 prefix가 비었는지 다시 조회하도록 보완했다. 관련 집중 검사 40개와 합성 PostgreSQL·MinIO 리허설이 통과했다. 이후 저장소 변경이 포함된 백업 후보 v4를 별도 고정했으며 운영 미설치다. 모든 스토리지 작성자의 펜스 참여와 취소된 I/O가 늦게 완료되는 경우는 여전히 무중단 백업의 미해결 조건이다. [스토리지 펜스 분석](STORAGE_WRITE_FENCE_2026-11-03.md).

해당 변경 후 API 전체 2,693개 통과·27개 건너뜀. 별도의 두 저장소 합성 시험에서 삭제 성공 후 commit 게시 실패 및 한 사본 소실을 재현했고, 살아남은 미결 intent가 복원 공개를 차단했다. [결과](acceptance/2026-11-03-single-replica-loss/result.json). 실제 운영에는 단일 GCS 기록만 연결돼 있으며 이중화·최신 표식의 독립성은 증명되지 않았다.

Neon S3 기록 조회에도 빈 페이지와 고유 토큰의 무한 반복 상한을 적용했다. S3/GCS·미러 집중 검사 19개와 [일회용 PostgreSQL·MinIO 리허설](acceptance/2026-11-03-neon-s3-boundaries/result.json)이 통과했다. GCS는 공개 접근 차단·soft delete 7일, 전용 VM 계정은 객체 생성·조회 권한을 갖는다. Neon 스토리지는 DB와 같은 분기에 속하고 기존 앱 자격으로 삭제도 가능해 변경 불가능한 독립 증인으로 입증되지 않았다. [백업 후보 v5](BACKUP_CANDIDATE_2026-11-03.md)는 최신 변경을 고정한 로컬 후보이며 운영 미적용이다.

최신 서버 후보는 [v14](../infra/gcp-pilot/narration-receipt-candidate-v14-manifest.json)다. 양 이미지의 소스 일치와 네트워크 차단·읽기 전용 migration head 검사는 통과했으나 운영 기반 이미지 동등성 및 실제 배포 승인은 없다.

별도 두 MinIO와 PostgreSQL을 사용하는 [이중 기록 요청 경로 리허설](acceptance/2026-11-03-mirrored-routes-retry/result.json)에서 동의 부여·철회, 프로필·캐릭터·책·계정 삭제와 공유·음성 철회의 outbox 및 양 사본 일치를 확인했다. 증인 저장 실패 때 삭제 커밋도 차단됐다. 당시 운영 런타임의 이중 기록 설정은 GCS 버킷용이고 Neon S3 증인 연결은 운영에 적용·검증되지 않았다. 두 GCS 버킷이 같은 프로젝트와 관리자 권한을 공유하는 경우 독립 장애 도메인이라 볼 수 없다.

후속 [이중 기록 인증 리허설](acceptance/2026-11-03-mirrored-routes-credentials/result.json)에서 합성 복구키 발급·교체와 계정 삭제 시 폐기, 증인 저장 실패 시 발급 롤백, commit 게시 장애 후 백그라운드 재시도를 검증했다. 실제 인증 정보나 운영 데이터는 사용하지 않았다.

이후 전용 자격의 S3 증인을 명시적으로 선택할 수 있는 런타임과 백업 전후 이중 기록 대조를 로컬에 구현했다. 기본 단일 GCS는 유지하며 불완전한 설정·같은 앱 자격 및 버킷 재사용은 거부한다. 합성 PostgreSQL·MinIO와 GCS 대역에서 한쪽 기록 누락 시 백업 발행 차단 및 서비스 재시작, 정상 백업을 확인했다. [검증 결과](acceptance/2026-11-03-gcs-s3-backup-final/result.json). API 전체 2,729개 통과·27개 건너뜀. 운영 연결, 독립 권한 및 최초 이관·최신성 보증은 아직 검증하지 않았다.

11월 3일 정규 일일 백업은 03:12 KST에 실제 시작해 03:14:42에 검증 성공 시각이 기록됐다. 서비스 종료 결과 success·exit 0, timer active이며 API·worker 컨테이너가 running으로 돌아온 것을 읽기 전용으로 확인했다. [관찰 결과](acceptance/privacy-final-synthetic-2026-11-03/scheduled-backup-observation.json). 실제 운영 복원 안전성이나 백업 중 무중단을 의미하지 않는다.

백업 이후 운영 `/health/ready`는 503이었다. DB·Redis·스토리지·작업 모니터는 정상으로 보고됐으나 AI 제공자의 최근 관측이 없어 `provider_runtime=unverified`였다. 원인은 만료 또는 관측 부재까지 특정되지 않았고 노출된 키를 호출하지 않았다. 낭독 전용 모드에서 미사용 STT가 준비 상태를 막는 문제와 Realtime TTS 성공 관측 식별자를 로컬 수정했으나, 이것이 현재 운영 503을 해결한 것은 아니다. 수정 포함 서버 v16과 백업 v7은 운영 미설치다.

추가 읽기 전용 진단에서 Redis의 OpenAI 글·그림 제공자 관측 키는 모두 없었고(TTL -2), 유효 기간 설정은 86,400초였다. 만료와 재시작·삭제는 구별하지 못했다. VM 내부 `/v1/config/capabilities`는 HTTP 200이었으며 확인된 운영 생성 가드는 `unavailable`만 차단하고 nginx에 readiness 기반 일괄 차단은 없었다. 일반 API 전체 차단으로 단정할 수 없지만 실제 생성 성공 증거도 아니다.

최신 서버 후보의 provider readiness 수정 이후 API 전체 테스트는 2,732개 통과·27개 건너뜀이다. Flutter 전체 테스트는 앞선 통합 검사 기준 701개 통과·2개 건너뜀이다. 실제 제공자 호출과 운영 준비 상태 정상화의 증거는 아니다.

후속 작업: S3 원장과 파기/백업 목록에서 KeyCount·prefix·버킷 정보가 모순되거나 예상 밖 공용 prefix가 있으면 실패 처리한다. 합성 MinIO·PostgreSQL 복원 리허설과 집중 검사를 통과했다. 앱은 프로필 전환 중 이전 책 제목 변경 응답이 새 프로필에 나타나지 않도록 보완했다. 키 교체 복구 표식이 기존 백업·배포 복구와 충돌할 때 옛 컨테이너를 재시작하지 않도록 로컬 격리 가드를 추가했으나, 실제 ingress 배수·systemd 부팅·키 전달과 운영 교체는 아직 미구현·미검증이라 운영 arm은 차단한다. 후속 전체 검사는 API 2,794개 통과·27개 건너뜀, Flutter 714개 통과·2개 건너뜀이다.

변경을 포함한 [서버 후보 v17](../infra/gcp-pilot/narration-receipt-candidate-v17-manifest.json)과 [백업 후보 v8](BACKUP_CANDIDATE_2026-11-03.md)을 로컬에 고정했다. 운영 설치와 복원은 승인되지 않았다. 키 교체 화면은 제한 권한 단일 키로 준비했지만 사용자가 실제로 키를 생성·입력했는지는 확인되지 않았다. 사용자 행동 없이 새 키가 존재하거나 운영 503이 해결됐다고 판단하지 않는다.

후속 모바일 변경: 새 책 본문 캐시는 계정별로 분리한다. 과거 공용 본문·읽기 기록·이미지는 소유자를 식별하지 못하므로 다른 계정 자료 손상을 피하기 위해 보존한다. 계정 삭제 후 해당 구 자료가 남으면 기기 정리를 완료했다고 표시하지 않고 안내 화면에 대기한다. 구 자료의 안전한 귀속 및 완전 파기는 미완료이며, 그 기기에서는 정리가 장기간 대기할 수 있다. 관련 Flutter 전체 검사 705개 통과·2개 건너뜀 및 분석 통과. 운영 앱 미배포다.

추가 모바일 변경: 책 본문·미디어·삭제 저널을 계정과 프로필별로 분리했다. 기존 계정 단위 자료는 자동 이관하지 않으며, 해당 계정 자료와 소유자 불명 공용 자료를 각각 별도 안내·명시적 확인 후 정리한다. 구 삭제 기록 때문에 모든 책이 막히던 업그레이드 경로도 바로잡고 해당 프로필의 해당 책만 차단한다. Flutter 전체 713개 통과·2개 건너뜀 및 정적 분석 통과 후 영수증 확인 전 GET 차단 등의 집중 검사 9개도 통과했다. 실제 기기·전원 중단 및 운영 검증은 남았다.

이 변경을 포함한 최신 서버 로컬 후보는 [v15](../infra/gcp-pilot/narration-receipt-candidate-v15-manifest.json), 백업 후보는 [v6](BACKUP_CANDIDATE_2026-11-03.md)이다. 후보 소스·마이그레이션 head 및 호스트 파일 고정을 확인했으나 운영 적용 근거는 아니다.

## 이번 작업의 경계

- 비공개 VM의 일일 백업과 기존 백업 실패 이메일 알림은 이전에 연결했다. 11월 3일 새벽 확인에서 백업 timer는 enabled·active, 서비스의 마지막 성공 시각은 11월 2일 13:31 KST, 다음 정규 예약은 11월 3일 03:11 KST였다. 해당 일일 예약 실행은 아직 관찰 전이며 현재 방식은 백업 중 API·worker를 일시 중지한다. 별도로 개인정보 파기 작업의 상태 감시 타이머와 이메일 정책을 설치하고 최초 정상 신호를 확인했다. 별도 임시 정책의 시험 실패·복구 신호로 Cloud Monitoring 경보의 발생·종료와 지정 이메일 두 건의 수신을 확인했다. 실제 운영 정책에 장애를 주입한 것은 아니다. 신호 부재 시험에서는 열린 사고가 나타났지만 해당 조건 및 이메일 수신을 확인하지 못했고, 운영 정책의 25분 부재 조건도 미검증이다.
- 로컬 앱·API에 책 삭제 확인 영수증, 계정별 미디어 저장 범위와 복구, 파기 미확정 표시를 보완했다. 구 서버가 계정별 범위 확인을 지원하지 않으면 삭제 API를 호출하기 전에 중단한다. 사진 동의 철회는 사진 관련 정리를 유지하면서 읽기·분기 진행률을 보존하고, 계정 삭제 시 진행률도 정리한다. 변경된 앱·마이그레이션과 범위 키는 운영에 적용하지 않았다. 구형 공유 캐시는 소유자와 책별 귀속을 판별할 수 없어 개별 삭제 시 물리적 완전 삭제를 보장하지 못한다. 계정·동의 정리 과정의 구 공유 캐시와 책 텍스트 캐시는 다른 계정에도 영향을 줄 수 있다. 디렉터리 fsync를 이식 가능하게 검증하지 못해 갑작스러운 전원 차단 시 저널 내구성도 보증하지 않는다.
- 음성은 사용자가 선택한 Google Gemini TTS의 세 스타일과 두 음색을 로컬 후보에 반영했다. 새 합성의 명백한 페이지·장면 안내는 제거하고 본문의 실제 문장은 보존한다. 결제 요청 횟수 제한은 기본 차단이며 금액 상한이 아니다. 운영 음성은 여전히 비활성이고 기존 캐시 음성은 자동 교체하지 않았다.
- 분리된 개인정보 파기 감시는 기존 운영 이미지 기준이다. `voice_sample_upload_guard` 취소 사유를 처리하는 새 감시 번들을 적용·검증하기 전에는 새 가족 음성 업로드 기능을 켜지 않는다.
- 네트워크가 차단된 합성 환경에서 마이그레이션 커밋·강제 종료 롤백, 백업 수신·복원 및 복원 DB 변조 거부를 확인했다. 복원 DB의 outbox와 백업 표식이 서명된 원장에 포함되는지 대조하고 불일치를 거부하는 검사도 추가했다. [복원 시험](acceptance/privacy-final-synthetic-2026-11-03/quarantined-adapter-synthetic.json), [원장 대조 시험](acceptance/privacy-final-synthetic-2026-11-03/witnessed-outbox-binding-synthetic.json), [후보 파일 고정](acceptance/privacy-final-synthetic-2026-11-03/candidate-v5-host-attestation.json). 관련 집중 검사 75개와 Ruff는 통과했다. 이는 실제 운영 백업 복원이나 최신 개인정보 변경의 완전한 재적용 증거가 아니다. 후보 기반 이미지는 운영 이미지와 동일성이 확인되지 않았다.
- 계정 범위용 키의 복구 자료를 Mac과 Google Secret Manager에 별도로 준비했다. Google의 고정 버전에서 자료를 읽어 메모리에서 복구하고 기대 해시와 일치함을 확인했으며, 복구 키를 파일에 쓰거나 운영 기능을 활성화하지 않았다. 이는 파일 출력 경로의 실제 복구나 Google 프로젝트 전체 상실 또는 동일 관리자 권한 침해에 대한 독립성을 보장하지 않는다.

## 반드시 남겨둘 작업

1. 최신 삭제·동의 철회·인증 폐기 기록이 원본 DB 상실 직전까지 독립적으로 완전함을 입증하고, 모든 저장소 버전·숨김 사본의 처리와 쓰기 차단을 검증한다. 격리 재적용기는 운영 대상 사용을 계속 거부한다. 음성 재동의 및 새 샘플 복원도 미완료다.
2. 운영과 동일한 이미지·설정으로 마이그레이션, 음성 예산·서비스 계정 권한, API·worker 및 백업을 단계적으로 검증하고 안전할 때만 배포한다. 실제 정규 일일 백업, 장시간 안정성, 복구 시간과 비용을 관찰한다. 백업 보존기간·용량 관리와 안전한 자동 정리 정책도 미완료다. 월 1만 원 Google 예산은 알림이며 강제 과금 중지가 아니다.
3. 실제 동화·삽화의 품질 및 사용자 승인 후 실제 기기의 생성부터 전체 낭독까지 검증한다. 로딩 화면을 포함한 전체 디자인 개선과 Android 검사는 사용자가 주요 기능 이후로 보류했다.
4. 노출된 API 키 교체는 사용자가 최종 보안 점검 때 한 번에 진행하도록 보류했다. 결제 기능도 후순위다.

기존 내용의 시험 시점은 [백업·삭제 복원 기록](BACKUP_DELETION_GUARD_2026-11-02.md), [음성 기록](NARRATION_STYLES_2026-11-02.md), [삭제 상태 화면](DELETION_STATUS_UI_2026-11-03.md)을 따른다.

### 실제 GCS 지연 쓰기와 PostgreSQL 연결 단절

운영 미디어 버킷은 운영자 자격의 시험 객체 생성과 조회를 모두 HTTP 403으로 거부했다. 운영 권한을 변경하지 않고 같은 프로젝트의 일회용 비공개 버킷과 일회용 PostgreSQL 16에서 재시험했다. 256 KiB 첫 조각의 HTTP 308을 확인한 후 공유 잠금을 보유한 PostgreSQL 세션을 강제 종료했다. 이어서 GCS가 마지막 조각을 받아 객체를 완성했고, 저장 바이트는 원본과 일치했다. DB 오류 이후 남은 미해결 쓰기 기록 때문에 백업 펜스 진입은 실패했다. 시험 객체는 세대 조건부 삭제 후 404로 확인했다. 이는 GCS JSON 재개 가능 업로드 시험이며 운영 Neon의 기존 직접 쓰기 권한 폐기나 진행 중 요청 종료를 입증하지 않는다.

### 운영 Neon 읽기 전용 자격 등록 후 확인

11월 4일 KST 운영 VM에서 별도 읽기 자격이 root 소유 0600 파일로 등록된 것을 확인했다. 등록 도구는 실제 시험 객체 읽기, 덮어쓰기·삭제 HTTP 403, 시험 객체 정리 뒤에만 이 파일을 발행한다. 등록 이후 재검사에서도 이 자격으로 원본 버킷 목록·멀티파트·버전 목록 조회가 성공했고 항목은 모두 비어 있었다. 새 임의 키에 대한 삭제는 HTTP 403이었다. 운영 API readiness HTTP 200, 백업 서비스 최근 결과 success, 공급자 갱신 타이머 active를 확인했다. v29 API·worker와 GCS 롤백 후보는 중지 상태였다. 기존 쓰기 자격은 아직 폐기하지 않았다. 전환 오케스트레이터의 독립 보호 조건을 연결하고 복구 경로를 확보한 뒤 폐기해야 한다.

복구 기록을 임시 파일에 완전히 쓰고 fsync한 다음 기존 파일을 덮어쓰지 않는 링크로 공개하도록 수정했다. 새 코드를 운영 복구 서비스에 설치하고 활성 전환 표식이 없는 상태에서 systemd 성공 및 API readiness 200을 확인했다. 동일 코드로 별도 GCE VM을 실제 재부팅한 결과 복구 표식이 보존되고 기록된 프록시·API·worker 다섯 컨테이너가 모두 stopped 및 restart=no였다. 시험 VM과 디스크 삭제도 확인했다. 같은 시점의 API 전체 검사 결과는 2,889개 통과, 27개 건너뜀이다.

운영 후보가 사용할 정확한 GCS HMAC 자격과 대상 버킷에 대해 새 전환 사전검사를 실행했다. 합성 키 한 개에만 만료 시간 있는 쓰기 권한을 부여한 상태에서 조건부 생성, 원본 바이트 읽기, 삭제 후 404가 확인됐다. 임시 권한을 제거했다. 운영 앱과 DB는 전환하지 않았다.

운영 DB에 TLS verify-full과 channel binding require로 연결해 읽기 전용 repeatable-read 트랜잭션에서 미디어 URL·JSON 참조와 미완료/실패 삭제 작업을 조회했다. 검사 대상 참조와 미완료 작업이 모두 없었다. 이 조회는 운영 쓰기를 중지하지 않았으므로 실제 전환 직전에는 원본 자격의 폐기 및 DB·저장소 쓰기 차단 아래 재검사해야 한다. 동일 시점의 공급자 타이머 최근 로그는 기존 관측 확인 24회였고 예약된 새 호출은 아직 없었다.

### 운영 전환 완료 조건 재점검

- 운영 Neon의 읽기 전용 자격은 검증됐다. Chrome 관리 화면에서 기존 쓰기 자격은 여전히 활성 상태였다. 운영 DB 읽기 전용 검사에서 미디어 참조와 미완료 파기는 없었고, GCS 복구 후보의 정지 상태·이미지·실행 명령·마운트·저장소 외 환경 일치도 확인했다. 기존 자격 폐기 후 새 요청의 401/403뿐 아니라 이미 승인된 쓰기가 종료됐다는 독립 증거가 필요하다.
- 최신 백업의 격리 복원과 합성 후속 개인정보·미디어 재적용은 검증됐다. 전환 어댑터가 같은 백업 기록의 건수·해시와 이후 이벤트 0건을 검증한 경우에만 마이그레이션을 진행하도록 변경했다. 새 코드를 사용한 운영 원본 펜스 아래 실제 전환 복원과 재공개는 아직 실행하지 않았다.
- 격리 VM 재부팅에서 새 복구 기록과 컨테이너 격리를 검증했다. 운영 호스트에는 복구 코드를 설치했고 전환 기록이 없을 때 정상 실행을 확인했다. 운영 전환 기록을 걸고 재부팅하는 시험은 아직 수행하지 않았다.
- 새 음성 이미지의 실제 Gemini 합성과 GCS 저장을 후보에서 검증했다. 운영 이미지 전환과 휴대폰에서 전체 낭독은 별도다.
- 운영 글·그림 갱신 타이머에는 갱신 후 관측을 재확인하는 코드가 설치됐다. 최신 로컬 코드의 음성 독립 갱신 분기는 아직 운영 적용 전이다. 예약된 실제 재호출도 아직 관측하지 않았다.
- 이 점검의 음성·복원 집중 테스트 144개, 운영 스크립트 Ruff 오류 검사, diff 공백 검사가 통과했다. 앞서 수행한 전체 API 2,889개 및 Flutter 720개 통과는 각 실행 시점의 결과다. 운영 오케스트레이터와 어댑터는 외부 쓰기 차단과 복구 증거가 연결되기 전까지 실행을 거부한다.

GCS XML 멀티파트 시험에서는 별도 비공개 버킷의 쓰기 권한으로 업로드를 열고 첫 파트를 저장했다. 해당 권한을 회수하고 목록 조회에서 인증 거부가 확인된 뒤 기존 업로드의 완료 요청도 401 또는 403으로 거부됐다. 첫 권한 전파 확인에 사용한 존재하지 않는 객체의 삭제는 404라 증거로 제외했다. 시험 업로드를 중단하고 임시 버킷을 삭제했다. 이 결과는 권한 회수 이후에 새로 보낸 GCS 완료 요청에 한정한다. 권한 회수 전에 이미 서버가 받아들인 완료 요청 또는 Neon 쓰기의 종료를 입증하지 않는다.

운영 VM에 호스트 포트를 열지 않는 v29 API 후보 `asb-narration-v29-portless-api`를 별도로 생성했다. 기존 v29 API 후보와 이미지·실행 설정·환경·마운트를 대조했고, 새 후보는 created 및 restart=no였다. 기존 v29 워커는 이미 호스트 포트를 게시하지 않는다. nginx의 HTTPS를 통해 readiness 신호를 전송하도록 운영 감시를 옮기고 실제 `ready: true`를 확인했다. 운영 API와 후보의 이름 및 트래픽은 전환하지 않았다.

v3 전환 기록은 공개 후 확인을 통과한 컨테이너의 ID와 이미지 ID를 기록한다. 별도 GCE VM에서 이 기록을 남기고 실제 재부팅한 결과 systemd가 새 API·워커·프록시 세 개만 시작해 자동 재시작 정책을 복구하고 기록을 제거했다. 이전 세대는 stopped 및 restart=no였다. API와 워커 응답은 시험용이며, 처음에는 시험용 게스트 스크립트 문법 오류가 발생해 정리 후 수정해 재실행했다. 두 시험의 VM·디스크 삭제가 확인됐다. 검증한 v3 복구 코드 해시를 운영에 설치했고, 전환 기록이 없는 상태에서 systemd 성공과 외부 HTTPS readiness 200을 확인했다.

운영 DB와 개인정보 원장 두 사본을 잠금 아래 다시 확인해 최신 상태의 서명된 체크포인트 3세대를 발행했다. 체크포인트 전용 임시 IAM 권한은 시험 후 제거했다. 최신 원격 백업을 격리 복원해 운영 체크포인트 4건과 복원 outbox 4건이 정확히 일치하는 것을 확인했다. 이후 미반영 기록은 0건이었고 실제 재적용 명령은 0건을 처리하며 격리 상태를 유지했다. 이 백업에는 미디어 객체가 없었고, 운영 대상 공개·전환 및 원본 상실 시 복원 권한은 확인하지 않았다.

실제 운영 Neon 미디어 버킷에 고유한 합성 키로 멀티파트 업로드를 시작하고 첫 파트를 저장했다. 공유 잠금을 가진 일회용 PostgreSQL 세션을 강제 종료한 뒤 Neon 완료 요청을 보냈고, 생성된 객체를 읽어 합성 바이트가 일치함을 확인했다. 미해결 쓰기 기록 때문에 일회용 DB의 백업 펜스는 발행 경로를 거부했다. 시험 객체와 멀티파트 상태를 정리하고 404를 확인했다. 운영 PostgreSQL은 이 장애 주입에 사용하지 않았다. 기존 Neon 쓰기 자격은 활성 상태였으므로 이 시험은 키 폐기 후 진행 중 요청 종료의 증거가 아니다.

운영 Neon 읽기 전용 키로 기존 쓰기 키가 만든 합성 멀티파트의 추가 파트 업로드, 완료, 중단을 각각 호출했다. 세 요청 모두 HTTP 403이었다. 기존 키로 시험 멀티파트를 중단한 후 객체 404 및 해당 업로드 ID가 목록에 없는 것을 확인했다. 읽기 전용 자격의 검증이며 기존 쓰기 키의 폐기나 폐기 전 승인된 요청의 종료를 입증하지 않는다.

운영 배포 후보 v29의 실제 API 경로로 가상 동화 한 페이지의 자연·구연·잠자리 스타일과 두 음색을 모두 합성했다. 여섯 조합 모두 HTTP 200이었고 MP3 바이트가 서로 달랐다. 실제 GCS에서 저장한 바이트와 원본을 대조하고 각 조합의 재요청이 추가 저장 없이 응답함을 확인했다. 합성 파일은 삭제 후 404로 확인했고 임시 쓰기 권한을 제거했다. 시험은 격리 SQLite와 가상 책을 사용했으며 음성 품질 청취·실기기·운영 배포 검증을 포함하지 않는다.

호스트 포트가 없는 GCS 복구 후보의 정확한 운영 API 이미지와 환경·마운트로 일회용 프로세스를 실행했다. 운영 DB 세션을 읽기 전용으로 제한하고, GCS 자동 버킷 생성이 꺼져 있는 것을 확인했다. 실제 readiness 코드에서 DB, Redis, GCS, 작업 조회, 제공자 관측이 모두 healthy였다. HTTP 서버나 Celery 워커를 기동하지 않았으며 실제 운영 서비스의 저장소는 아직 전환하지 않았다.

저장소만 전환하는 기존 이미지 후보에 맞춰 운영 VM에 v30 백업·공급자 갱신 설정 세 파일을 스테이징했다. 대상은 GCS이고 API·워커 이미지는 현재 운영과 동일하다. 개인정보 원장 연결은 현재 설정과 일치한다. 파일은 root 소유 0600이며 기존 활성 설정은 교체하지 않았다.

저장소 전환과 음성 배포가 사용하는 이전 컨테이너 이름을 분리했다. 전환 전에 이름 충돌을 확인하며, 재부팅 복구는 같은 단계의 API·워커 한 쌍과 정확한 컨테이너·이미지 ID를 요구한다. 서로 다른 단계가 섞이면 복구가 거부되고 이미 다시 시작된 것으로 확인된 프록시가 중지된다. 로컬 Docker에서 정지·백업·마이그레이션·공개 단계마다 실행 프로세스를 강제 종료했다. 공개 시험에서는 워커 이름만 일부 바뀐 상태로 중단했으며 다섯 컨테이너가 모두 중지되고 자동 재시작이 해제됐다. 격리 GCE VM의 실제 재부팅에서는 공개 기록에 지정된 API·워커·프록시만 복구됐으며 시험 VM·디스크는 삭제를 확인했다. 동일한 복구 코드를 운영에 설치해 systemd 실행 성공, 전환 기록 없음 및 HTTPS readiness 200을 확인했다.

운영 VM에 스테이징된 정확한 v30 GCS 자격으로 합성 객체 하나를 생성·바이트 대조·삭제했다. 첫 시도는 호스트 Python 모듈 경로 누락으로 중단됐고, 경로를 수정한 재시험은 성공했다. 단일 객체에만 허용한 만료 조건부 IAM 권한은 두 시도 모두 제거를 확인했다. 이 자격은 운영 앱의 활성 쓰기 자격으로 전환하기 전이다. 운영 공급자 갱신 스크립트는 최신 코드로 교체했고, 실제 운영 API 컨테이너 대상 무과금 실행이 성공했다. 예약 타이머의 유료 재호출은 아직 관측하지 않았다. 최신 전체 API 회귀는 2,903개 통과·27개 건너뜀, 이후 집중 회귀는 152개 통과다.

운영 VM에서 확인한 가용 메모리는 약 404 MiB였다. 저장소 전환 어댑터는 이제 별도 호스트의 격리 복원 결과를 Ed25519 서명으로 검증할 수 있다. 전환의 일회용 요청 번호·백업 ID·매니페스트 해시·DB 리비전·원장 건수와 해시에 서명을 묶고, 응답을 받은 후 DB 펜스와 원장·매니페스트·저장소를 재확인한다. 복원 호스트는 DB·미디어를 검증한 뒤 복원 outbox를 별도로 서명된 운영 개인정보 체크포인트에 대조한다. 운영 원장의 암호화 키는 복원 호스트에 전달할 필요가 없다. 전환용 서명은 운영 복원 공개 권한을 부여하지 않는다.

운영 DB와 개인정보 원장 두 사본을 잠금 아래 비교해 4세대 체크포인트를 발행했고, 한시적 GCS 권한을 회수했다. 실제 최신 원격 백업의 매니페스트를 운영 VM의 로컬 매니페스트와 대조한 뒤 Mac의 네트워크 없는 컨테이너에 복원했다. 첫 복원 이미지에서 비특권 프로세스가 소스 디렉터리를 읽지 못해 확인이 중단됐고, 이미지 권한을 수정하고 부팅 시 읽기 검사를 추가해 재시험했다. DB·미디어와 복원 outbox 4건이 서명된 체크포인트와 일치했고 새 복원 서명을 확인했다. 해당 백업에는 미디어 객체가 0건이었으며 격리 컨테이너를 제거했다. 검증은 최근 백업을 대상으로 했고 실제 운영 전환 중 새 백업을 주고받는 명령 및 운영 전환은 남아 있다.

11월 4일 실제 운영 저장소 전환 명령을 실행했다. 사전 검사는 동일한 운영 이미지, 사전 스테이징 설정, 독립 감시기의 실제 큐 조회, 비어 있는 두 저장소, 운영 DB 리비전 및 개인정보 원장 4건을 확인했다. 공개 요청을 잠시 닫고 큐를 비운 뒤 새 백업을 생성했다. Mac 격리 복원의 서명이 운영 VM에 도착했고, 그 후 운영 VM이 GCS 후보 API·워커를 시작했다. 첫 SSH 연결은 최종 응답 전에 만료됐고 후보는 공개 전 검증에서 중단됐다. 정확한 최초 예외는 보존되지 않아 원인 확정에는 추가 재현이 필요하다.

기존 Neon API·워커·프록시를 정확한 기존 ID로 복구했다. 12:16:01 KST에 복구 기록 제거와 서비스 자동 재시작 정책 복구가 확인됐고, 외부 HTTPS readiness 200 및 기존 워커의 실제 응답을 확인했다. 외부 접속 중단은 약 21분이었다. 대상 GCS에 한시적으로 부여한 쓰기 권한은 회수했다. Neon 기존 쓰기 자격은 여전히 운영에서 사용한다. 재기동 시 실제 API 준비에 약 2분 37초, 워커 확인에 약 2분 10초가 걸렸다. 이후 로컬 코드는 저장소 전환과 이전 구성 복구에서 API 준비 확인 후 워커를 시작하며, SSH가 끊겨도 실패 지점을 확인할 수 있도록 VM 로그에 단계명을 남긴다. 이 수정으로 운영 전환을 재시도하기 전이다.

전환 VM의 복원 서명 교환을 단일 SSH 파이프에서 VM의 root 전용 일회용 파일로 옮겼다. `run_pilot_media_detach.py --execute --mailbox <32자리 hex>`는 VM에서 독립 실행하고, 별도의 연결에서 같은 계획과 작업 ID로 `--read challenge`, `--sign`, `--read result`를 실행한다. 서명 입력은 정확한 도전 값과 계획의 공개 키에 맞을 때만 게시되며, 파일을 덮어쓰지 않는다. 복원 호스트는 `verify_pilot_media_detach_backup.py`에 도전 JSON을 stdin으로 넣는다. `--recover-original`은 공유 잠금 아래 미공개 v2 기록, 기존 이미지·컨테이너 ID·이름과 중지 상태가 일치할 때만 순차 복구한다. 실행 중인 기존 워커나 이름이 바뀐 세대는 건드리지 않는다.

실제 운영 전환 시도에서 생성한 최신 백업으로 재연결 시험을 했다. 최초 시험에서 조회 명령이 불필요하게 DB 초기화를 요구하는 문제를 발견해 제거했다. 두 번째 시험에서는 첫 SSH 연결을 실제로 닫은 뒤 새 연결에서 복원 요청을 읽어 격리 복원하고 서명을 제출했다. VM은 개인정보 4건과 백업의 일치를 확인했다. 이 백업의 미디어 객체는 0건이며 시험은 운영 트래픽을 변경하지 않았다. 실제 PostgreSQL의 SHARE 잠금을 유지한 별도 Docker 환경에서 현재 API와 실제 Redis·Celery를 순차 기동해 준비 상태와 큐 검사도 확인했다. 이 기동 시험은 모의 AI 제공자를 썼다. 실제 운영 워커의 가동 중 큐 검사는 약 40초였다.

독립 systemd 작업으로 운영 저장소 전환을 다시 시도했다. 운영 사전 검사, 큐 비우기, 새 백업의 외부 격리 복원 및 서명, 후보 API 순차 시작, 워커 응답과 격리 큐 검사는 통과했다. 공개 단계의 중복 API·워커 재검사에서 예외가 발생했다. 컨테이너 이름 변경과 활성 설정 교체 전에 중단된 사실을 확인했다. 해당 예외는 API와 워커를 합친 메시지를 기록했으므로 둘 중 어느 하위 검사가 실패했는지는 확정하지 못했다. 운영 외부 접속 중단은 약 16분이었다.

`--recover-original`을 별도 VM 작업으로 실행해 기존 API·워커·프록시와 자동 재시작 정책을 복구했다. 정확한 기존 ID, 복구 기록 없음, 외부 HTTPS readiness 200 및 한시적 GCS 쓰기 권한 제거를 확인했다. Neon 쓰기 자격과 운영 데이터베이스는 기존대로 사용 중이다. 로컬 공개 코드는 격리에서 확인한 컨테이너 ID·이미지·실제 기동 시각·재시작 횟수를 180초 안에 재확인하고, 이름 변경 후 프록시가 실제 API 경로에서 readiness 200을 받는지 검사한다. 격리 Docker의 실제 PostgreSQL 잠금 아래 API·Celery 확인과 컨테이너 이름 변경, nginx 경유 HTTP 검사를 통과했다. 별도 시험에서 컨테이너 재시작 후 기존 검증을 거부했다. 이 수정은 아직 운영 전환에 사용하지 않았다.

11월 4일 13:01 KST에 시작한 세 번째 운영 전환은 기존 워커의 큐 배수 확인에서 종료됐다. Docker 이벤트상 워커 내 확인 프로세스는 약 63.4초 뒤 종료 코드 0으로 끝났고, VM의 전환 도구는 60초 제한에서 먼저 반환했다. 백업이나 새 이미지 기동 단계에는 진입하지 않았다. 운영 워커를 계속 실행한 채 동일한 기존 API와 프록시를 복구했다. 13:07 KST까지 외부 HTTPS readiness 200, 실제 워커 응답, 기존 세대의 자동 재시작 설정, 복구 기록 제거 및 임시 GCS 쓰기 권한 회수를 확인했다. 운영 상태에서 다시 실행한 동일한 읽기 전용 큐 검사는 약 47.6초에 통과했다.

다음 후보는 공개 경로를 닫기 전에 기존 워커에 동일한 읽기 전용 큐 검사를 실행한다. 기존·신형 워커에 각각 최대 150초의 검사 예산을 부여하고, 배수 재시도 전체는 300초로 제한한다. 실패할 경우 고정된 진단 메시지만 기록한다. 큐 응답, DB, 브로커 검사를 유지했다. 관련 집중 회귀 91개가 통과했다.

이 후보로 기존 API를 운영한 채 전체 사전 검사를 재실행했다. 첫 실행에서 운영 워커 큐 검사가 약 82초에 통과했지만 호출 측 SSH의 160초 제한으로 최종 결과를 받지 못했다. VM의 독립 systemd 작업으로 다시 실행한 결과 운영 저장소·큐·개인정보 원장 4건을 포함한 사전 검사가 통과했다. 시험용 GCS 임시 권한을 제거했고, 새 운영 전환은 실행하지 않았다.
