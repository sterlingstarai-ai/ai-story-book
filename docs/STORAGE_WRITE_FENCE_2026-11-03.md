# 저장소 쓰기 펜스 검토 — 2026-11-03

현재 운영 백업의 API·worker 중단을 유지한다. PostgreSQL advisory lock만으로는 모든 S3 작성자가 멈췄다는 것을 증명할 수 없으므로, 이 문서는 읽기 전용 운영 모드의 활성화 승인이나 무중단 백업 구현이 아니다.

## 애플리케이션 쓰기 경로

`apps/api/src/services/storage.py`의 쓰기 경계는 `upload_bytes`, `upload_image_from_url`, `upload_file`, `copy_object_to_new_key`, `_delete_prefix_keys`, `delete_keys`다. 이미지 생성·교정, 등장인물 사진, 페이지 마스크, 동화 삽화 복사, 오디오와 음성 샘플이 업로드 또는 복사를 사용한다. 파기 큐는 prefix·개별 키 삭제를 호출하고 오케스트레이터도 정리용 개별 키 삭제를 호출한다. API와 Celery worker 양쪽에서 이러한 경로가 도달 가능하다. 현재 이 함수들이 공통 DB advisory lock을 취한다는 근거는 없다.

앱에서 발견한 presigned URL은 `get_object` 다운로드용이다. 이것은 다른 프로그램이나 자격 소유자가 직접 PUT·DELETE할 수 없다는 증거가 아니다. `scripts/run_approved_book_acceptance.py`처럼 별도 S3 클라이언트를 직접 만드는 운영성 도구도 존재한다. 개인정보 기록용 별도 저장소 클라이언트와 복원·시험 도구의 직접 쓰기도 앱의 미디어 어댑터 밖에 있으므로 버킷별 역할과 대상 범위를 따로 확정해야 한다.

## 공통 잠금 적용 전 해결할 조건

1. API·worker의 모든 배포본과 유지보수·수동 도구, 제공자 대시보드 및 별도 자격의 미디어 버킷 쓰기 권한을 식별한다. 잠금을 모르는 작성자가 남으면 S3를 동결했다고 판정하지 않는다.
2. 이미 수락된 요청과 각 프로세스의 백그라운드 스레드를 드레인한 뒤에만 배타 잠금을 취한다. `storage._call_s3`는 동기 boto3 호출을 스레드로 실행하고 음성 업로드에도 별도의 타임아웃·실패 가드가 있다. 요청 취소나 DB 세션 종료만으로 원격 PUT이 끝났다고 추정하면 안 된다.
3. 협력 작성자는 실제 객체 변경 전에 공통 shared 잠금을 얻고 원격 응답·결과 판별이 끝날 때까지 유지해야 한다. DB 연결 상실 시 잠금이 해제되는 동안 스레드·네트워크 호출이 계속될 수 있으므로, timeout·프로세스 강제 종료·네트워크 분리 및 미확정 쓰기의 영속적인 격리를 별도로 증명해야 한다.
4. 동의 철회·삭제는 잠금 대기 또는 유지보수 중 성공으로 표시하지 않는다. 파기 지시는 내구성 있게 남기고 부분·미확정 상태를 표시하며, 서비스 재개 뒤 남은 객체와 공급자의 버전·soft-delete까지 검증한다.
5. 합성 환경에서 업로드·복사·prefix/키 삭제 각각에 대해 백업 잠금과 동시에 시작/취소/응답 유실/연결 중단을 재현한다. 운영 전 모든 작성자의 런타임 동일성 및 외부 접근 통제를 증명한다. 스냅샷·미디어의 일관성과 최신 개인정보 기록의 완전성도 별도로 필요하다.

## 함께 고친 삭제 완료 판정

미디어 prefix 삭제는 S3 목록의 `IsTruncated`가 누락·비불리언이거나 이어가기 토큰이 누락·반복되면 미완료로 남기고 페이지 수를 제한한다. 실제 객체를 삭제한 뒤에는 새 목록 조회로 빈 prefix를 확인한다. 이 재조회는 그 시점의 증거이며 이후 늦게 도착하는 업로드나 공급자의 숨은 버전까지 차단하지 않는다. 관련 집중 검사 40개와 [일회용 PostgreSQL·MinIO 리허설](acceptance/2026-11-03-storage-prefix-verification/result.json)이 통과했다. 운영 반영은 하지 않았다.

## 공통 잠금 합성 실험

시험 전용 어댑터로 일회용 PostgreSQL·MinIO에서 PUT·copy·delete가 shared advisory lock에 참여하도록 하고 배타 잠금 중 세 작업이 시작되지 않음을 확인했다. 이미 실행 중인 작업의 호출자 취소가 성공하지 않아 shared 잠금이 유지되는 동안 배타 잠금이 차단되는 것도 확인했다. 이 실험은 실제 앱의 asyncio 취소 처리를 검증하지 않는다.

같은 실험에서 진행 중 작업의 PostgreSQL 세션을 종료하자 shared 잠금이 해제됐고, 배타 잠금이 잡힌 상태에서도 별도 S3 copy가 실제로 완료됐다. 작업은 DB 연결 상실을 나중에 감지해 성공을 반환하지 않았지만 저장소 변경 자체는 이미 일어났다. 따라서 **DB advisory lock만으로 연결 상실 후 진행 중 S3 호출의 완료를 봉쇄할 수 없다**. [합성 리허설](acceptance/2026-11-03-storage-cooperative-fence/result.json)은 일회용 자원을 정리했다. 실제 API와 worker에는 시험 어댑터를 연결하지 않았으며 운영 백업의 중단 방식은 그대로다.

후속 합성 실험에서는 **같은 DB 세션의** session-level shared 잠금을 얻은 뒤 S3 요청 전에 in-flight 의도를 자동 커밋하는 모델을 시험했다. 세션을 강제 종료해도 미완료 기록이 남아 시험용 백업 판정이 차단됐고, 배타 잠금을 보유한 동안 늦게 성공한 PUT 이후에도 기록은 미완료로 남았다. 같은 operation ID의 재시도는 기존 PUT 전후 모두 추가 쓰기를 하지 않았다. 또한 의도 커밋은 실제 성공했으나 호출자에게 응답이 유실된 상황을 코드로 주입해 S3가 시작되지 않고 기록이 미완료로 남는 것을 확인했다. [합성 리허설](acceptance/2026-11-03-storage-durable-intent-v2/result.json), `synthetic-storage-write-fence.log`. 커밋 응답 유실은 실제 네트워크 중단이 아닌 코드 주입이며, 백업 차단도 독립 시험용 판정이다.

이 모델은 첫 단계의 가능성을 보여줄 뿐 실제 앱·worker·백업 스케줄러와 연결되지 않았다. 모든 작성자·외부 자격의 참여, 모든 DB·객체 상태 전이, asyncio 취소, 프로세스 강제 종료·복구와 독립 객체 보존 정책에 대한 증거가 없으므로 운영 활성화와 무중단 백업을 승인하지 않는다. 미확정 의도는 자동으로 성공 처리하지 않으며 별도 안전한 재대조가 필요하다.

## 시험 전용 공통 구현

`scripts/synthetic_storage_intent.py`에 동일 세션의 shared lock, 선커밋 intent, 동기 저장소 작업, 완료 기록을 묶은 공통 시험 함수를 분리했다. 명시된 loopback 테스트 환경 외에는 실행되지 않으며 앱·worker·백업 스케줄러에 연결되지 않는다. 예외 또는 모호한 응답 때 pending을 유지하고, 이미 존재하는 operation ID는 완료 여부와 상관없이 원격 작업을 반복하지 않는다.

기존 세션 강제 종료·늦은 PUT·중복 재시도·커밋 ACK 유실 주입에 더해 정상 copy/delete 및 완료된 ID의 재실행 거부를 일회용 PostgreSQL·MinIO에서 확인했다. [합성 전체 리허설](acceptance/2026-11-03-synthetic-durable-module/result.json). ACK 유실은 실제 네트워크 절단이 아니라 코드 예외이며, 외부 작성자·실 앱의 asyncio 취소·운영 장애 복구를 증명하지 않는다. 운영 플래그와 새 마이그레이션도 추가하지 않았다.
