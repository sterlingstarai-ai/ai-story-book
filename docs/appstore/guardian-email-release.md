# 보호자 이메일 확인과 Play 데이터 보안

## 현재 상태 — 2026-11-11

최신 API·워커 소스는 운영에 적용했지만 실제 SMTP 비공개 설정이 없어 보호자 메일 기능은 꺼져 있다. 빌드 4는 양쪽 스토어에 업로드됐고 iOS 내부 베타에 배정됐다. 아래 빌드 2와 별도 후보 이미지의 '미업로드·미배포' 설명은 해당 시점의 과거 기록이다.

Play 초안에는 이메일 주소 수집, 비일시 처리, 보호자 확인을 위한 앱 기능·보안/규정 준수 목적을 추가했다. 삭제 URL을 공개 삭제 요청 페이지로 맞추고 5/5 미리보기에서 임시보관함 저장을 확인했다. 메일 업체의 보유·공유 예외와 최종 운영 설정은 미확인이다. 따라서 초안의 '제3자 공유 없음' 요약을 확정 사실로 인용하거나 그대로 제출하지 않는다. [현재 제출 후보와 남은 확인](submission-checklist.md#현재-제출-후보--2026-11-11)

## 구현·검증 이력

2026-11-10 Play 게시 개요에 비공개 테스트 Alpha 1.0.0(1)과 미제출 변경사항 12개가 표시된다. 콘솔이 차단 사유로 타겟층 및 콘텐츠 선언, 데이터 보안 선언 미완료를 표시한다. 앞서 입력한 타겟 범위는 만 0~12세다. 기존 업로드를 새 앱의 근거로 사용하지 않는다.

서명한 Android AAB와 iOS IPA 1.0.0(2)은 로컬 `docs/acceptance/2026-11-10-guardian-email/`에 보관했다. Android는 기존 업로드의 인증서와 일치하고, iOS는 앱 식별자·빌드 번호·배포 서명을 검증했다. 운영 VM에서 API·워커에 보호자 메일 설정이 없는 것을 확인했다. 공개 운영 API는 준비 상태에 응답하며 보호자 메일 확인 경로는 404다. 두 후보 모두 스토어에 올리지 않았다.

검사: 실제 임시 Redis와 가상 메일 발송을 사용하는 서버 검사 31건, OpenAPI 계약 5건, Flutter 검사 32건 통과. SMTP 발송 실패 후 재요청 가능, 동의 링크 단순 조회 시 미승인, 계정 간 분리, 철회 뒤 링크 재사용 거절을 확인했다. 실제 메일 발송과 앱 스토어 심사 경로는 이 검사에 포함되지 않는다.

2026-11-11 로컬 TLS 서버와 실제 SMTP 클라이언트로 STARTTLS와 암시적 TLS를 각각 확인했다. 두 방식에서 인증과 메시지 전송은 암호화가 설정된 뒤에만 발생했다. 가상 주소와 인증값을 사용했으며 외부 발송 업체의 배달 검증은 남아 있다.

앱은 처음 아동 정보 처리에 동의할 때만 보호자 주소를 받는다. 메일을 열기만 하면 아무 일도 일어나지 않으며, 안내를 읽고 직접 동의한 뒤에만 앱이 확인한다. 산수 잠금과 사진의 별도 동의는 유지한다. 이메일 주소는 앱 DB와 백업 동의 기록에 쓰지 않는다. 발송 제한에는 주소의 해시가 10분, 확인 요청과 토큰에는 계정 범위가 30분 유지된다. 발송 업체가 남기는 메일과 배달 기록의 보관은 별도로 확인한다.

| Play 신고 항목 | 새 빌드 기준 |
|---|---|
| 개인 정보 → 이메일 주소 | 수집함. 보호자 확인과 계정 관리·법규 준수 목적으로 사용. 확인이 필요한 기능에는 필수다. |
| 일시 처리 | 발송 업체의 보관 정책을 확인할 때까지 일시 처리로 체크하지 않는다. |
| 공유 | 선정한 발송 업체의 계약이 Google Play의 서비스 제공업체 예외에 해당하는지 확인한 뒤 체크한다. |
| 암호화 | 앱→API HTTPS, API→발송 서버 SMTP TLS 설정과 실제 연결을 확인한다. |
| 계정 삭제 | 기존 앱 내 삭제와 공개 삭제 요청 주소를 확인한다. 발송 업체의 배달 기록은 업체별 정책을 확인한다. |

제출 전 순서:

1. 운영 발송 업체, 인증 정보 파일, 실제 공개 HTTPS 주소를 설정한다. 확인 경로는 브라우저에서 접근할 수 있어야 한다. API와 워커를 동일한 동의 정책으로 구성하며, 발송 비밀번호 파일은 API에만 읽기 전용으로 제공한다. 기본값은 꺼짐이다.
2. 실제 이메일로 가상 계정의 발송·동의·재접속을 검증한다. 법정대리인 확인으로 사용할 수 있는 절차인지 검토하고, 운영 방침에 발송 업체와 처리·보관 사항을 반영한다. 이메일 링크 확인을 법령이 예시한 회신 방식과 동일하다고 전제하지 않는다.
3. Play 심사 계정이 개인정보 없이 동작하는지 확인하고, 새 서명 빌드, 방침, 데이터 보안, 심사 안내를 일치시킨다. 게시 개요에서 실제 검토 제출 여부를 확인한다.

프로덕션 Compose에 `infra/docker-compose.guardian-mail.yml`을 함께 적용하면 `GUARDIAN_EMAIL_SMTP_HOST_PASSWORD_FILE`의 기존 파일만 API에 읽기 전용으로 연결한다. 파일은 컨테이너 실행 사용자 소유와 권한 `0600`이 필요하다. 발송 업체에 맞춰 `GUARDIAN_EMAIL_SMTP_SECURITY=implicit_tls`와 포트 465 또는 `starttls`와 업체 지정 포트(통상 587)를 설정한다. STARTTLS 연결에서 암호화를 시작하지 못하면 로그인 전에 중단한다.

심사용 가상 계정은 예약 후 `python -m scripts.provision_store_review request-consent`에 슬롯과 운영자가 관리하는 시험 이메일을 JSON 표준 입력으로 넘긴다. 메일에서 확인한 뒤 `finalize-consent`에 슬롯을 넘겨 동의와 개인정보 저널 기록을 완료한다. 심사 패스는 확인을 마친 슬롯만 배정한다. 일반 계정의 동의 조건은 동일하며 심사 안내에는 메일함 자격 증명 대신 기존 심사 패스를 넣는다. [Play 심사 접근 안내](https://support.google.com/googleplay/android-developer/answer/15748846?hl=en)

2026-11-11 후보는 최신 보호자 동의가 DB에 저장되고 독립 개인정보 저널에도 게시된 후에만 해당 슬롯을 준비 완료로 표시하고 심사 패스로 배정한다. 격리 PostgreSQL에서 저널 게시 실패를 주입해 DB 커밋 뒤에도 배정을 거절하고, 동일 이벤트 재게시 후에는 배정을 허용하는 것을 확인했다. 계정 복구와 실제 Redis 보호자 동의 프로토콜을 포함한 23개 검사가 통과했다. 운영에는 이 수정본을 적용하지 않았으며 공개 준비 경로는 200, 보호자 확인 경로는 404였다.

심사 슬롯 예약에서 메일 요청, 링크 열기, 보호자의 명시적 확인, 동의 기록과 심사 패스 사용까지 한 흐름으로 연결해 검사했다. 격리 PostgreSQL·Redis와 실제 HTTP 확인 라우트를 사용했고 SMTP 전송만 가로챘다. 링크를 열기만 하거나 저널 게시가 실패한 상태에서는 심사 접근이 차단됐다. 같은 기록을 재게시하자 심사 패스로 해당 계정에 접근할 수 있었다. 고정 FastAPI 0.162.0에서 OpenAPI 계약을 포함한 28개 검사가 통과했다. CI의 PostgreSQL 작업에 전용 시험 Redis를 연결했다. 실제 운영 메일 수신은 별도로 검증한다.

운영 대상과 같은 `linux/amd64` 로컬 후보 두 개를 빌드했다. API `asb-guardian-api:review-20261111031849`의 이미지 ID는 `sha256:d67a3aba27e4cc0a3a03a65f6f65b33ed1f6cd089acbabc49135b7485fe60587`, 워커 `asb-guardian-worker:review-20261111031849`는 `sha256:7503f3e57ba303c2fa2400b7b678c017011a671abc5eae4ca0df5320c08be0a4`다. 네트워크를 끈 컨테이너에서 두 이미지의 최신 심사자·개인정보 저널 소스 해시와 비루트 실행을 확인했다. API의 OpenAPI 계약이 저장소와 일치했고, 메일 설정 없이 보호자 기능을 활성화하면 메일 준비 검사에서 503이 발생했다. 워커는 같은 보호자 설정으로 Celery를 불러왔다. 후보를 레지스트리에 올리거나 운영에 적용하지 않았다.
