## 현재 경계

## 독립 시제품

`apps/mobile/lib/services/book_media_store.dart`는 로컬 작업본에서 표지·본문·분기 동화·인페인트 이미지와 본문 낭독 경로에 연결한 실험용 서비스다. 새 미디어는 별도 앱 전용 디렉터리에 계정별·책별로 저장하며, 이전 공유 캐시는 **읽기 전용**으로만 조회한다. 각 파일의 이름은 미디어 식별자의 SHA-256이며, 같은 계정에서 여러 프로필이 공용 책을 읽어도 파일을 중복된 프로필 영역에 남기지 않는다. 다른 계정 영역과 다른 책 영역은 분리한다. 앱 배포나 실기기 검증은 아직 이뤄지지 않았다.

- 서버 삭제 요청 전에 `beginDeletion`으로 요청 표식을 기록하고 신규 파일 쓰기를 차단한다. 표식에는 책 ID, 요청마다 새로 생성한 임의 ID, 원래 프로필의 불투명 해시를 넣는다. 서명 URL과 인증 비밀은 넣지 않는다.
- 같은 서버·계정 영역과 원래 프로필, 같은 요청 ID의 서버 삭제 확정이 확인된 경우에만 `confirmDeletion`과 `purgeBook`을 사용한다. `pendingRequests`는 현재 영역의 미확정 요청만 돌려준다. 서버 결과가 불확실하면 표식을 유지한다. `rejectDeletion`은 동일 범위에서 요청이 확실히 거부됐다는 증거가 있을 때만 사용한다.
- 파기는 같은 인스턴스에서 진행 중인 다운로드가 끝나기를 기다리고, 늦게 끝난 다운로드는 삭제 표식 때문에 공개 경로로 이동하지 못한다. 대기 시간 초과나 실제 파일 삭제 실패는 미완료로 남긴다. 재시작 후 `retryPending`은 이미 서버에서 확정된 파기만 재시도한다. 완료 후에도 표식을 유지해 오래된 화면이 파일을 다시 쓰지 못하게 한다.
- 심볼릭 링크로 책 디렉터리를 바꿨을 때 외부 경로를 파기하지 않도록 검사한다. 다른 책의 로컬 파일이나 읽기 진행률을 전체 삭제하지 않는다.

합성 Flutter 테스트는 다른 책 보존, 서버 미확정 요청의 재시작, 다른 계정·프로필 거부, 이전 응답 ID 거부, 지연 다운로드, 파기 실패 재시도, 시간 초과와 경로 이탈 거부를 확인했다. 별도 대상 파일 두 개의 `flutter analyze`도 통과했다.

## 앱 연결 전에 필요한 결정과 검증

1. 서버 범위 식별자와 삭제 영수증은 아래와 같이 로컬 코드에 추가됐으나 운영 DB 마이그레이션·키 설정·서버 배포는 하지 않았다. 프로필 선택이 바뀐 뒤 이전 요청을 새 프로필의 인증으로 무심코 재시도하지 않는다. 서버가 현재 자격과 기존 범위가 같은 계정임을 확인한 경우에만 분리된 로컬 영역의 쓰기를 중지하고, 충돌하지 않는 책과 삭제 기록을 이관한다. 같은 책의 폴더나 삭제 기록이 충돌하면 덮어쓰지 않고 양쪽을 보존하며 보류한다. 인증 전 또는 다른 서버·계정이라고 확인된 영역은 합치지 않는다.
2. 네트워크 단절 후 404만으로 같은 계정·프로필의 이전 삭제 요청이 확정됐다고 단정할 수 없다. 401·403도 삭제 완료 증거가 아니다. 미확정 요청은 보류하고 새 서버의 영수증으로만 확인한다. 구 서버에서는 영수증 재확인이 불가능하므로 서버 요청과 로컬 삭제 표식 생성을 시작하지 않고 사용자에게 안내한다. 과거에 이미 생성된 미확정 표식은 계속 보존한다. 서버 미디어 파기 완료는 별도다.
3. 삭제 요청과 계정별 정리 대상 계획은 앱 지원 디렉터리에 파일을 flush한 뒤 원자적 이름 교체로 기록하고 SharedPreferences에 미러링한다. 동일 대상의 동의 정리에서 계정 정리로 진행하는 경우를 제외한 불일치는 보수적으로 중단한다. 계획에는 종류를 기록하며, 환경설정 표식이 유실된 뒤 파일로 복구할 때는 기존 자격의 계정 범위를 확인한다. 키가 없거나 다른 자격이면 새 계정을 생성하거나 파기를 추측하지 않고 중단한다. Dart에서 디렉터리 자체의 fsync를 이식 가능하게 수행하지 못하므로 갑작스러운 전원 차단 내구성과 실제 프로세스 강제 종료를 검증하기 전에는 완료를 보장하지 않는다. 서버 삭제 요청 전 `account_requested` 계획을 비파괴적으로 기록하고, 응답이 유실되면 같은 자격으로 서버에 재확인한다. 확정되기 전에는 로컬 파기를 하지 않는다. 디렉터리 기록이 전원 장애에서 사라질 수 있는 한계는 그대로 남는다.
4. 새 저장소는 단일 인스턴스·단일 isolate를 전제로 하며, 연결된 책 이미지·음성은 새 파일을 공유 캐시에 쓰지 않는다. 삭제 표식이 생기면 현재 뷰어의 낭독을 중지하고 이미지 메모리를 비운다. 다만 과거 앱·다른 프로세스의 쓰기, 앱 종료와 플랫폼 캐시의 상호작용은 실기기 검증 전이다.
5. 기존 DefaultCacheManager 파일의 소유 매핑이 없는 경우는 안전한 선택적 삭제나 다른 책의 오프라인 보존을 동시에 증명할 수 없다. 원본 사용 내역에 근거한 검증 가능한 이관 방법과 불명 파일 정책을 정한 뒤, 실제 iOS·Android 재시작·오프라인·동시 다운로드·서버 부분 실패를 시험해야 한다.

## 서버 기준 계정 범위 시제품

`GET /v1/account/media-scope`는 인증된 요청에 한해 서버의 내부 소유자 ID를 반환하지 않고, 별도 비공개 키로 도메인 분리 HMAC한 64자리 식별자를 반환한다. 복구 코드로 기기 인증을 교체해도 서버가 같은 소유자를 확인하면 같은 식별자이며, 계정 삭제 후에는 인증이 거부된다. 이 식별자는 비밀 자격증명이나 접근 권한이 아니다. 계정 내 여러 프로필에 같은 범위가 나타나므로 화면과 서버는 기존 프로필별 책 접근 검사를 계속 강제해야 한다. HTTP 응답은 `private, no-store`다.

이 기능만 사용하는 별도 32바이트 난수 키 파일, 해당 파일의 SHA-256 pin, 안정된 서버 네임스페이스가 모두 필요하다. 파일은 컨테이너 실행 사용자 소유·비공개 정규 파일이어야 하고 심볼릭 링크는 허용하지 않는다. 키가 없거나 권한·pin이 맞지 않으면 이 엔드포인트만 503이며 기존 세션과 앱 부팅은 변경하지 않는다. 키 본문을 환경변수, 로그 또는 저장소에 넣지 않는다. `infra/docker-compose.account-scope.yml`은 관리자가 선택했을 때만 읽기 전용 키 파일을 API에 연결하는 override다.

**아직 운영 설정·키 생성·배포는 하지 않았다.** 같은 서버를 이전하거나 과거 DB를 복원해도 동일 범위를 얻으려면 키와 pin, 네임스페이스를 별도로 안전하게 보존·복구해야 한다. 키 또는 네임스페이스가 바뀌면 범위도 바뀐다. 현 구현은 과거 키 목록이나 구 범위 자동 이관을 지원하지 않으므로 클라이언트는 식별자 불일치 시 기존 로컬 데이터·미확정 요청을 새 범위로 임의 이전하거나 삭제하지 말고 보류해야 한다. 구 서버가 이 엔드포인트를 제공하지 않으면 기존 콘텐츠를 보존하고 새 책 삭제 요청을 시작하지 않는다.

`scripts/account_scope_key.py`는 별도의 기존 32바이트 복구 키로 새 스코프 키를 감싼 뒤 비공개 파일과 pin 참조를 생성하거나 복구하는 도구다. 기본 실행은 dry run이며 `--execute`를 명시해야 한다. 기존 파일은 덮어쓰지 않고 키 원문을 출력하지 않는다. 부분 실행은 비활성 상태로 남는다. 복구 키·암호화 봉투·검증 참조를 동일 기기나 동일 관리자에게만 두면 독립 재해 복구가 성립하지 않으며, 별도 보관과 실제 복구 검증 없이 운영 키를 활성화하지 않는다.

`gen-lang-client-0308507618`의 Secret Manager에 아래의 새 비밀 세 개를

- 암호화된 스코프 키 봉투: `asb-account-scope-encrypted-envelope-4694f9065c7e3e72`
- 봉투 및 키 참조: `asb-account-scope-pinned-reference-4694f9065c7e3e72`

복구 키와 봉투는 서로 다른 비밀이지만 **동일한 Google 프로젝트와 관리자
장애 영역**에 있다. Google 관리자 계정 침해나 프로젝트 손실로 함께
노출되거나 없어질 수 있으므로 독립 관리라고 취급하지 않는다. 반대로
Google 프로젝트만 없어지고 Mac이 유지되면 Mac 원본을 사용할 수 있으며,
Mac만 없어지고 Google 접근이 유지되면 Google 사본으로 복구할 수 있도록
준비한 상태다. 둘 중 한쪽에서 실제 복구가 가능한지 아직 검증하지 않았다.
Secret Manager 사용량은 계정 전체의 무료 한도와 기존 사용량에 따라 비용이
발생할 수 있다. [Google 요금 안내](https://cloud.google.com/secret-manager/pricing).

아래 명령은 정상적인 Google CLI 인증을 마친 별도 기기에서 특정 버전의 세
비밀을 메모리로만 받아, 사전에 기록한 namespace와 키 SHA-256을 대조하고
새 비공개 파일에 복구하도록 준비한 절차다. 반환된 키는 여전히 비활성이며,
복구 후 실제 서비스에 연결하지 않는다. 이 스크립트와 복구 경로는 아직
실행·시험하지 않았다. 지문은 키 원문이 아니다.

```sh
./apps/api/venv/bin/python scripts/recover_account_scope_from_gcp.py --execute --project gen-lang-client-0308507618 --recovery-secret asb-account-scope-recovery-key-4694f9065c7e3e72 --envelope-secret asb-account-scope-encrypted-envelope-4694f9065c7e3e72 --reference-secret asb-account-scope-pinned-reference-4694f9065c7e3e72 --namespace pilot-20261103 --expected-key-sha256 2dc0ebea7a56b77f277ce07467b027faa9cf2f627cb4a651d7d6f53483d06fe3 --output /absolute/private/recovery-directory/restored-scope.key
```

`scripts/account_scope_offline_backup.py`는 이 복구 키, 봉투 및 pin을
운영자가 별도로 보관하는 암호구로 다시 암호화한 단일 복구 패키지를 새
파일로 만드는 도구다. 암호구는 숨김 입력으로 받고 출력·환경변수·명령행에
넣지 않으며, 20자 이상이어야 한다. 패키지를 저장할 디렉터리는 현재 사용자
소유의 접근 권한 `0700`이어야 하고 기존 파일을 덮어쓰지 않는다. 최종
검증 때만 실제로 분리된 매체와 별도 보관된 암호구를 확보한 후 다음 명령을
사용한다. 이 도구 및 명령은 아직 실행하거나 시험하지 않았다.

```sh
./apps/api/venv/bin/python scripts/account_scope_offline_backup.py create --execute --recovery-key-file /Users/jmac/.asb-account-scope-inactive-bg0h4r1c/recovery/recovery.key --envelope-file /Users/jmac/.asb-account-scope-inactive-bg0h4r1c/envelope/scope-key.envelope --reference-file /Users/jmac/.asb-account-scope-inactive-bg0h4r1c/envelope/scope-key.reference.json --package /absolute/private/external-directory/account-scope.backup
```

패키지 사본과 암호구는 서로 다른 장소에 보관한다. 동일 Mac의 다른 폴더,
동일 물리 디스크의 다른 파티션, 또는 단순한 클라우드 폴더 존재만으로는
별도 장애 영역이 아니다. 외부 매체의 독립성과 패키지·암호구에 대한 실제
접근을 확인하고, 별도 비공개 경로에 복구하는 다음 절차와 pin 검증을 최종
시험하기 전까지 계정 범위 기능은 운영에 활성화하지 않는다.

```sh
./apps/api/venv/bin/python scripts/account_scope_offline_backup.py recover --execute --package /absolute/private/external-directory/account-scope.backup --key-output /absolute/private/recovery-directory/restored-scope.key
```

## 서버 삭제 영수증 시제품

선택적 `X-Deletion-Request-Id`를 사용한 책 삭제는 책 행 삭제·파기 대기열·요청 영수증을 같은 데이터베이스 트랜잭션에 기록한다. 같은 계정·책·원래 프로필·요청 ID로만 재확인이 가능하고, 같은 ID를 다른 책이나 프로필에 재사용하면 거부한다. 계정 복구 후 새 기기 자격은 같은 소유자로 확인되지만 이전 자격은 차단된다. 프로필을 삭제하면 그 프로필의 영수증을 제거하고, 계정 삭제 시 해당 계정의 영수증을 제거한다. 다른 프로필에 속한 책이나 다른 계정의 영수증을 이 확인으로 열 수 없다.

영수증은 **책 행 삭제가 커밋됐다는 사실만** 증명한다. 응답 유실 후 재조회 시 저장소 파기는 `unknown`이며 완료를 주장하지 않는다. 삭제 이벤트의 선택적 암호화 개인정보 기록에 요청·프로필 범위를 포함해 격리 복원기에서 책 삭제 적용 후 영수증을 재구성한다. 기존 기록에 해당 필드가 없으면 과거 지문과 형식을 유지한다. 운영용 최신 기록 완전성·복원 격리는 여전히 미승인이다.

## 후속 로컬 구현 범위

서재에는 현재 프로필의 미확정 삭제 또는 미완료 파기를 다시 확인하는 항목을 추가했다. 이 동작은 영수증을 조회할 뿐 다른 계정이나 다른 프로필의 요청을 대신 실행하지 않는다. 영수증이 없거나 404·403·통신 오류이면 기존 요청과 파일을 보존한다. 구 서버에서 새 삭제는 시작하지 않으며 기존 데이터와 표식을 보존한다.

사용 중인 자격이 같은 서버 계정 범위를 확인한 뒤에만 기존 로컬 영역을 연결·이관한다. 두 영역의 쓰기를 중지하고 저널을 먼저 보존한 뒤, 충돌하지 않는 책 디렉터리를 같은 파일시스템에서 이동한다. 같은 책 디렉터리 또는 삭제 요청 기록이 충돌하면 둘 다 보존하고 중단한다. 일시 중단 중에는 화면에서 확인 안내를 표시한다. 이관과 실제 파일 소유 범위, 앱 강제 종료 후 재개는 합성 테스트 및 실기기 검증 전이다.

계정 삭제·동의 철회 시 새 책별 저장소는 현재 계정에 연결된 범위만 정리한다. 정리 대상 계획은 기존 자격이 교체되기 전에 별도로 기록하며, 재시작 시 보안 저장소에서 이전 자격을 불러오거나 보존된 계획을 재사용한다. 다른 계정의 새 저장소와 삭제 표식은 보존한다. 과거 `DefaultCacheManager` 공유 캐시는 소유 계정을 구분할 수 없어 기존 전체 정리 경로의 영향이 남는다. 구버전 전역 텍스트 키도 계정별 소유 구분이 없어 같은 한계가 있다. 동의 철회는 진행률과 선택 기록을 보존하며, 계정 삭제는 해당 구버전 전역 진행률도 정리한다.
