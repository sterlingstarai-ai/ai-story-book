**red 증거 (수정 전 코드, 실PG + 실 Celery 워커)**
```

AssertionError: 실 PG + 실 Celery 워커에서 2연속 책 생성이 done에 도달하지 못했다 — C1 회귀.
  job statuses=[('queued', None), ('queued', None)]
1 failed in 375.49s (0:06:15)
```
**green (수정 후)** — `3 passed in 36.06s`

**⚠️ 내 초기 주석 주장 정정(측정으로 반증됨).** "NullPool 과 run_async 통합은 각각 독립 방어선" 이라고 적었다가 실제로 확인했다: **워커 신호를 끄고(=NullPool 없이) 통합만 남기면 2연속 테스트가 여전히 FAIL 한다**(78.75s, 재확인 완료). 태스크 #1 이 루프를 닫으며 풀에 남긴 커넥션을 태스크 #2 의 새 루프가 재사용하기 때문이다.
→ **NullPool 이 load-bearing**, `run_async` 통합은 *한 태스크 안에서* 실패 마킹 경로까지 함께 죽던 2차 결함을 없애는 방어선. 코드 주석을 이 측정 결과대로 정정했다(`database.py`, `tasks.py`).

**회귀 테스트** `apps/api/tests/test_celery_worker_pg.py` (3종)
1. `test_sequential_run_async_survives_on_postgres` — 오케스트레이터·Celery 없이 원인만 격리 + 풀 클래스가 NullPool 인지 확인
2. `test_worker_completes_two_sequential_book_jobs` — **실 워커 subprocess** 로 태스크 2연속 → 둘 다 `done`
3. `test_worker_records_failure_and_refunds_on_error` — 실패가 `failed` 로 **기록**되는지(수정 전엔 실패 마킹 경로도 죽어 `queued` 잔류)

> 하네스 자체도 `asyncio.run` 을 반복하므로 **테스트 엔진을 NullPool 로 고정**했다. 그러지 않으면 하네스가 검증 대상과 같은 이유로 죽어 제품 결함과 구분되지 않는다(첫 실행에서 실제로 그렇게 실패했다).

### 🟡 A1 — 에러 위생 (CTO 추가 발견)

**보고서보다 심각한 것을 발견**: 누출은 pydantic 덤프만이 아니었다. `LLMError.details = {"raw_output": text[:500]}` — **모델 원문 응답**이 그대로 클라이언트로 나갔다(미검열 생성물 유출 경로).

`main.py` 에 순수 함수 `sanitize_domain_error()` 도입:
- 메시지: `SAFETY_INPUT`/`SAFETY_OUTPUT` 만 원문(사용자가 조치 가능) — 나머지는 일반 문구
- details: 화이트리스트(`suggestions`·`page`·`retry_after`·`reason`)만 — `raw_output` 은 절대 불가
- 원문·detail 키 목록은 **로그로만**(진단 정보 유지)

**일반화 점검**: `str(e)` 가 클라이언트 응답으로 들어가는 경로를 라우터·코어·서비스 전수 grep. 도메인 에러 경로는 이 핸들러 하나로 수렴하며, 그 외 `raise *Error(...)` 는 전부 고정 문구 + 구조화 details 였다. 추가 누출 지점 없음.

## 4. 스코프 밖 발견 — **수정하지 않고 보고**

### ⚠️ S1 — 페이지 재생성이 mock 에서 **조용히 실패**한다 (매트릭스 #22 는 false-pass 였다)

`POST /v1/books/{job_id}/pages/{n}/regenerate` 는 **200 을 반환하지만**(잡 등록만 성공) 백그라운드 잡이 실패한다:
```json
{"event":"Regeneration job failed",
 "error":"[LLM_JSON_INVALID] 응답 검증 실패: 2 validation errors for RewriteResult
          page  Field required ... revised_text  Field required ...",
 "regen_job_id":"regen_20260809_060433_2dcb32f5","page_number":2}
```
- **원인**: mock LLM 의 프롬프트 분기에서 `rewrite_page_text.system.jinja2` 가 "스토리" 분기에 걸려 **StoryDraft 모양**을 돌려주는데, 엔드포인트는 `RewriteResult{page, revised_text}` 를 기대한다. M3(retell)와 **같은 클래스**의 mock 커버리지 결함이다.
- **내 변경과 무관함 확인**: 새로 넣은 retell 분기는 `"original_pages" in user_prompt` 또는 `"연령대(target_age)" in system_prompt` 로 걸린다. `rewrite_page_text.system.jinja2` 는 둘 다 0 매치(실측), `original_pages` 를 가진 템플릿은 `rewrite_story_for_age.*` 뿐이다. → **기존 결함**.
- **왜 지금까지 안 보였나**: 엔드포인트가 200(잡 등록)만 돌려주므로 중간 E2E 도 200 만 보고 #12/#22 를 PASS 로 기록했다. **내 이번 재검증도 같은 함정에 빠졌다가 워커 로그에서 잡았다.**
- **파급**: 실키 환경에서는 프롬프트가 지시한 스키마로 응답할 가능성이 높아 동작할 수 있으나, **mock E2E 로는 페이지 재생성을 영원히 검증할 수 없다**(M3 와 동일한 사각지대).
- 이 사실을 M3 커버리지 테스트 docstring 에 명시하고, 그 테스트가 검증하는 범위를 "fallback 센티널로 떨어지지 않음"으로 **정직하게 한정**했다(스키마 정합까지 보려면 프롬프트별 기대 타입 매핑이 필요 — 별도 티켓 후보).

### ℹ️ S2 — 성장 리포트 레벨 라벨이 **서버에서 한국어 고정**

`GET /v1/growth` 의 `reading_level.label` 이 `"첫 걸음"`·`"꾸준히 성장"` 같은 한국어를 그대로 내려준다. M6 에서 클라이언트 **폴백**은 현지화했지만, 서버가 값을 주면 en/ja 사용자에게 한국어가 노출된다. 서버측 로컬라이즈(M15 잔여)와 같은 묶음이라 이번 범위 밖으로 남긴다.
