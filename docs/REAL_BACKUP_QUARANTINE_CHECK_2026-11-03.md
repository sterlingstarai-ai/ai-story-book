# 실제 백업 격리 복원 확인 — 2026-11-03

## 서명 체크포인트 대조 추가

최신 원격 완료 표식과 운영 VM의 로컬 manifest가 일치하는 백업을 다시 네트워크 차단 tmpfs에 복원했다. 서명 영수증과 암호화 헤드·체크포인트를 Mac에서 별도 검증한 뒤, 복원 DB의 개인정보 이벤트 4건의 ID 집합과 전체 해시가 서명 관측과 정확히 같은 것을 확인했다. 관측 시점 기준으로 재적용할 후속 이벤트는 0건이었다. 미게시 기록 0건, 백업 미디어 객체 0개, 격리 컨테이너 제거를 확인했다. 실제 후속 이벤트 변경 시험과 비어 있지 않은 미디어 복원은 합성 환경 결과만 있으며, 이 운영 백업 시험은 서비스 재개를 승인하지 않는다.

사용자 요청에 따라 운영 VM·GCS의 최신 백업을 읽기 전용으로 확인하고, 소유한 로컬 Docker의 네트워크 차단·tmpfs 컨테이너에 스트리밍해 복원했다. 운영 DB·스토리지·서비스는 변경하지 않았으며, 백업·개인정보·자격 원문을 Mac 일반 파일이나 보고서에 저장하지 않았다. 운영 복원 또는 서비스 공개 승인은 이 확인의 범위가 아니다.

- 운영 VM 백업 세트의 파일 해시·목록 검사와 PostgreSQL 16 `pg_restore --list`가 통과했다. 원격 GCS의 최신 완료 표식이 지정한 manifest와 VM 최신 로컬 manifest의 해시가 같았다. DB 백업 크기는 186,740바이트, 미디어 객체는 0개, 복원 전 revision은 `5de7a40b6c12`다.
- 완료 표식·manifest·백업 본문을 검증해 네트워크가 없는 임시 메모리 파일시스템으로 전달하고 격리 PostgreSQL·MinIO에 복원했다. 복원된 DB fingerprint와 미디어 목록을 백업과 비교해 일치를 확인했다.
- 처음에는 최신 outbox 대조기가 이전 스키마에 없는 `deletion_receipt` 열을 무조건 조회해 대조에 실패했다. 해당 열 추가 전의 명시된 revision 세 개와 정확한 구형 열 집합에 한해 NULL로 읽도록 보완하고, DB revision과 manifest를 비교했다. 모르는 revision, 불완전한 migration, 구형과 신형의 열 불일치는 거부한다. 수정 후 실제 백업을 다시 격리 복원해 backup checkpoint의 outbox 4건 및 전체 fingerprint 일치, 미게시 0건을 확인했다.
- 별도 읽기 전용 관측에서 운영 DB outbox와 당시 관측한 GCS 개인정보 원장은 4건으로 일치했고, 최신 백업 checkpoint의 개수·fingerprint도 같았다. 이는 관측 시점의 일치이며 외부 원장이 독립적으로 완전하고 가장 최신이라는 증명은 아니다. 활성 쓰기가 존재할 수 있어 복원 후 최신 변경을 모두 재적용할 수 있다고 판정하지 않는다.
- 격리 컨테이너와 그 tmpfs는 사용 후 소유권을 확인해 제거했다. 백업 원본을 운영 DB·객체 저장소에 덮어쓰거나 변경하지 않았다.

변경한 재적용기의 삭제 대상 목록 검증은 잘못된 버킷·접두사·KeyCount·CommonPrefixes·이어가기 토큰과 중복 목록을 거부한다. 초과 목록은 실패 처리한다. 네트워크가 없는 합성 PostgreSQL·MinIO에서 계정 삭제·동의 철회·인증 교체·미디어 접근 차단·재실행 멱등성을 확인한 결과는 `docs/acceptance/2026-11-03-replay-inventory-validation/offline-restore-544a2c1e2459907ff136206151cea0bb.json`에 있다. 집중 pytest 77개와 스키마 단위 검사 3개, Ruff가 통과했다.

남은 조건: 복원한 구형 스키마의 적절한 마이그레이션과 최신 원장의 독립적 완전성, 삭제·동의 철회·인증 폐기의 모든 후속 사건 재적용, 저장소 버전/숨은 사본 처리 및 모든 쓰기 경로의 펜스가 필요하다. 위의 실제 데이터 복원 및 현재 원장 대조는 서비스 공개 가능성을 뜻하지 않는다.
