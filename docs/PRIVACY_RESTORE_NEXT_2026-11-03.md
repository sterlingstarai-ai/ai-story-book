# 운영 복원: 개인정보 최신 기록의 다음 작업

## 확인된 범위

- 실제 백업은 네트워크가 차단된 별도 환경에서 복원해 검사했다. 별도 읽기 관측에서 운영 DB outbox, 당시 GCS 원장, 백업 checkpoint의 건수와 fingerprint가 4건으로 일치했다. 세 관측이 모든 작성자를 동시에 멈춘 원자적 증거이거나, 독립 보관소가 최신 기록을 모두 가지고 있다는 증거는 아니다. 상세 결과는 `REAL_BACKUP_QUARANTINE_CHECK_2026-11-03.md`를 따른다.
- 저장소 소스의 `hold_consistent_source`는 같은 PostgreSQL advisory lock을 사용하는 개인정보 작성자만 막는다. `live_privacy_boundary.py`는 펜스가 유지되는 동안 DB outbox와 원장을 다시 대조하지만, 작성자 전체 포함 여부와 독립 최신성을 `false`로 보고한다. 로컬 소스의 존재가 현재 운영 이미지의 해당 동작을 증명하지는 않는다.
- 독립 witness의 봉인·연결된 head와 장애 시 원본 유실 시험은 합성 데이터로 준비돼 있다. 외부에서 보호되는 최신 head, 독립 복구키·권한, 모든 작성자 통제와 운영 모니터 연결은 확인되지 않았다. 구체적 한계와 합성 결과는 `PRIVACY_WITNESS_CHECKPOINT_2026-11-02.md`를 따른다.

## 바로 이어 할 최소 작업: 하나의 폐쇄된 복원 경계 실증

운영 데이터를 바꾸지 않고, 현재의 `live_privacy_boundary.py`와 witness checkpoint를 일회용 PostgreSQL 및 두 개의 독립된 합성 저장소에 연결하는 단일 검증 경로를 완성한다. 검증 입력은 전부 가상 사용자·동화로 만들고 실제 사용자 키, 실제 운영 저장소, 서비스 URL이나 운영 복원 대상을 넣지 않는다.

1. 펜스 획득 전후에 삭제·동의 철회·인증 폐기 요청을 각각 발생시킨다. 같은 잠금을 사용하는 요청이 경계 동안 대기하고, 경계 해제 뒤 기록돼 다음 checkpoint에 포함되는지 확인한다. 잠금을 사용하지 않는 임의 DB/저장소 작성자가 있으면 해당 경계는 완전성 증거가 아님을 결과에 표시한다.
2. 펜스를 보유한 동안 outbox와 두 원장 일치, pending 부재, 고정된 head 기록과 read-back을 검사한다. 응답 유실·부분 기록·DB 연결 단절·서로 다른 witness·오래된 head는 실패로 처리하고, 불확정 상태에서 재생이나 공개 성공을 반환하지 않는다.
3. 장애 직전의 독립 head와 키만으로 백업을 격리 복원해 후속 삭제·동의 철회·인증 폐기를 순서대로 재적용한다. 누락·변조·중복·원장 한쪽 유실과 최신 head 미확정도 각각 검출한다. 객체 버전과 숨은 사본의 처리 여부는 별도 결과로 남긴다.
4. 산출물에는 격리 환경의 고유 식별, 합성 데이터 사용, 동시 쓰기·오류 주입 결과 및 정리 결과를 기록한다. 모든 경우 `restore_authorized: false`를 유지한다. 이미 존재하는 개별 시험을 통합한 결과이며, 성공해도 운영 최신성·24시간 무중단이나 실제 복원을 증명하지 않는다.

## 운영 반영의 별도 증거

운영을 복구하려면 현재 배포된 이미지의 모든 개인정보 변경 경로와 외부 저장소 작성자를 식별하고 펜스 참여를 증명해야 한다. 또한 운영 장애와 독립된 곳에서 최신 head와 복구키를 보호하고, 승인된 쓰기 직후부터 head 확정 전까지의 실패를 실제로 처리해야 한다. 이 두 조건은 위의 합성 시험만으로 충족되지 않는다. 최신 head나 미확인 작성자가 남으면 복원본은 격리된 상태로 두고 실제 데이터 완전성을 주장하지 않는다.

## 2026-11-03 합성 통합 실행 결과

네트워크 없는 일회용 컨테이너에서 PostgreSQL 두 개와 MinIO 두 개를 실행해 [결과](acceptance/2026-11-03-privacy-boundary-synthetic/result.json)를 얻었다. 공통 fence를 사용하는 합성 기록 세 건은 경계가 열린 동안 대기했고, 두 원장의 한쪽 객체 유실과 기존 trusted head보다 오래된 head는 거부됐다. 별도 합성 복원 시나리오에서는 계정 삭제·동의 철회·인증 변경 재적용과 반복 실행을 확인했다. 동시성 시나리오와 복원 시나리오는 **동일한 사건의 단일 연쇄가 아니며**, 생산 데이터나 독립 관리자·생산 백업의 실제 최신성은 시험하지 않았다. 모든 결과에서 복원 공개 권한은 `false`이고 시험 자원 정리는 확인됐다.

중요한 반증도 확인했다. 같은 격리 DB에서 공통 advisory lock과 원장을 거치지 않는 직접 프로필 삭제는 fence가 유지되는 동안 실제로 성공했다. 이는 해당 fence만으로 전체 작성자 통제나 최신 이력을 보장할 수 없다는 뜻이다. 운영 복원 전에는 실제 이미지·DB·저장소의 모든 쓰기 경로를 봉쇄하거나 공통 경계에 참여시켜야 하며, 독립적으로 보관되는 최신 head와 복구키도 별도로 마련·검증해야 한다.
