# 2026-10-21 로컬 실행 복구

시작일은 10월 21일이며 최종 보완·검증은 10월 22일(KST)에 이어서 수행했다.

현재 소스로 브라우저 검토용 빌드와 별도 PostgreSQL·Redis·Celery·MinIO 환경을 실행했다. AI는 결정적인 시험 대역이며 공개 배포, 실제 AI 품질, 스토어 제출 완료를 뜻하지 않는다.

## 복구한 문제

- Docker가 시작하며 2026-03-14 생성된 `infra-api-1/2`, `infra-worker-1/2`, `infra-nginx-1`을 자동 복귀시켰다. 구형 API의 Docker 표시는 healthy였으나 `/health/ready`는 503이며 DB·Redis·작업 감시가 모두 unhealthy였다. nginx는 TLS 인증서가 없어 반복 종료했다.
- 이 다섯 컨테이너만 `restart=no`로 변경하고 정상 종료했다. 기존 데이터 볼륨, 인증서 설정, 다른 프로젝트의 컨테이너는 변경하지 않았다. 구형 이미지를 다시 서비스하지 않도록 보존한 상태이며 공개 TLS 요건은 유지한다.
- Flutter 웹의 API 주소 계산이 `Platform.isAndroid`에서 `Unsupported operation: Platform._operatingSystem`으로 실패했다. Chrome에서 기존 테스트의 실패를 재현한 다음 웹에서는 네이티브 플랫폼 API를 호출하지 않도록 수정했다. 네이티브 Android 에뮬레이터 기본 주소와 릴리스 HTTPS 검사는 유지한다.
- 실제 Chrome에서 부모 동의 화면이 표시되는 동안에도 StoreKit2 플랫폼 채널 오류가 발생했다. 결제 SDK의 즉시 초기화를 지연하고 웹의 네이티브 구매 스트림을 비활성화했다. Chrome의 macOS/Android 플랫폼 식별 두 경우를 회귀 검사하며 실제 결제의 검증·소비·복원 순서는 바꾸지 않는다.
- 수정 뒤 일반 새로고침에서도 이전 StoreKit 오류가 재발했다. 현재 HTTP와 디스크 JS의 SHA-256은 같지만 오류가 가리키던 328178행은 최신 빌드에서 숫자 포맷 코드였다. 브라우저의 이전 번들 캐시 사용을 확인했고, 서비스워커와 HTTP 캐시의 영향을 배제하도록 단순 `http.server`를 프리뷰 전용 서버로 교체했다. 해당 origin의 Flutter 워커 등록만 해제하고 `no-store`와 빌드 해시별 JS 주소를 사용한다. localStorage·IndexedDB·CacheStorage·쿠키를 삭제하지 않는다.
- 기존 격리 실행 도구에 `--serve`, `--api-port`, `--web-origin`을 추가했다. 합성 HTTP 여정이 통과한 뒤 API와 worker를 유지하며, 종료 시 해당 실행이 만든 자원만 정리한다. 지정 포트에 다른 서버가 있어도 이 실행의 고유 응답 헤더를 확인하기 전에는 데이터 변경 검사를 시작하지 않는다.

## 현재 검토 주소와 재실행

- 브라우저 검토: `http://127.0.0.1:18281/preview`
- 격리 API: `http://127.0.0.1:18280`
- 최신 실행 근거: Git 제외 `docs/acceptance/2026-10-21-local-preview-final/`
- API 소스는 비밀 설정 파일을 제외한 임시 복사본이다. 원본 설정과 기존 사용자 자료를 사용하지 않는다. 재시작 시 합성 시험 데이터가 새로 만들어진다.

```bash
./scripts/run_runtime_e2e.sh --suite media --serve --api-port 18280
# 다른 터미널에서 apps/mobile 디렉터리로 이동한 뒤:
flutter build web --debug --no-wasm-dry-run --dart-define=API_BASE_URL=http://127.0.0.1:18280
python3 ../../scripts/serve_web_preview.py
```

가상 입력으로만 검토한다. 브라우저 화면은 네이티브 사진 선택·음성·결제 플러그인의 실기기 검증을 대신하지 않는다. 정식 제품 대상은 Android와 iOS이며 이번 웹 산출물은 비공개 debug 검토본이다.

API 실행 터미널에서 Ctrl-C를 누르면 해당 API·worker와 이 실행의 PostgreSQL·Redis·MinIO 컨테이너 및 임시 자료만 정리된다. 웹 서버 터미널의 Ctrl-C는 18281 정적 서버만 종료하며 빌드는 남는다. 다른 프로젝트나 기존 데이터 볼륨을 정리하는 명령을 사용하지 않는다.

## 실제 확인한 범위

- Flutter 환경 설정·결제 구매/복원 집중 회귀 native 35개 통과. Chrome에서 환경 주소 시작 오류 1개와 네이티브 결제 비활성 2개 통과. 변경 파일 정적 분석 통과. debug 웹 빌드 성공.
- 실제 PostgreSQL·Redis·Celery·비공개 MinIO를 통한 미디어 접근 검사 19항목과 합성 이미지 캐릭터 승인·12쪽 생성·동의 철회 삭제 26항목 통과. 전체 HTTP 사용자 여정 통과. 유료 AI나 실제 아동 사진은 사용하지 않았다.
- `/health/live`는 200. `/health/ready`는 DB·Redis·저장소·작업 감시 healthy, mock 제공자 때문에 의도적으로 503. 이를 운영 준비 완료로 바꾸지 않았다.
- 허용한 로컬 브라우저의 CORS 사전 요청은 200, 외부 origin은 400이며 허용 헤더가 없다.
- 포트 충돌 시험에서는 기존 서버에 `/health/live` 조회만 보냈고 변경 요청은 0회였다. 실행은 실패로 종료하고 소유한 임시 자원을 정리했다.
- `--serve` 실행의 정상 종료를 직접 확인했고 정리 결과 `completed`를 기록했다. 마지막 검토 실행은 별도로 유지한다.
- 프리뷰 HTTP의 HTML·bootstrap·워커·JS 응답은 모두 200/no-store이며, 과거 날짜 캐시를 유지할 수 있는 조건부 요청에도 304를 보내지 않는다. 최신 JS SHA-256은 `87a11e6df3c0e729be7c46e1e1045be4c4ac51e8860011565f5effafc71975cc`다. 검증 기록은 최신 acceptance 폴더의 `cache-verification.json`이다. 실제 브라우저 콘솔도 이 빌드 식별자로 대조하며, 첫 화면 표시만으로 오류가 없다고 판정하지 않는다.
- 최종 실제 Chrome 검수 완료: 2026-10-22 00:08:20 KST(`2026-10-21T15:08:20.148Z`)에 빌드 해시가 붙은 새 JS의 `app_open`을 확인했다. 그 이후 새 앱 오류는 없으며, 로그에 남은 15:04:50 UTC 오류는 이전 번들이다. 접근성 트리와 실제 스크린샷에서 부모 동의 문구·체크박스·비활성 시작 버튼이 정상 표시됐다. 동의 선택이나 실제 자료 입력은 하지 않았다.

## 공개 출시까지 남은 항목

기존 운영 설정으로 실행한 외부 사전 검사는 여전히 `BLOCKED`다. 공개 API·HTTPS 저장소 주소, 실 공급자 구성과 이용 관측, 검토 중인 공개 개인정보처리방침·약관 확정, 실제 배포·스토어 연결은 이번 로컬 복구로 충족되지 않는다. 기존 월 정기 호스팅 보류를 새로운 결제 승인으로 간주하지 않았다.

이 로컬 복구 당시에는 Xcode 전체 앱 없이 Command Line Tools만 선택되어 있어 iOS 빌드·서명·업로드를 검증하지 못했다. 이후 2026-10-22 Xcode 27.1 설치로 해소된 네이티브 단계는 [iOS 빌드 복구 기록](IOS_TOOLCHAIN_RECOVERY_2026-10-22.md)을 따른다. 대규모 기존 미커밋 변경은 그대로 보존했고 이번 로컬 복구에서는 커밋·푸시·스토어 제출을 하지 않았다.

검토 범위는 이번 환경 주소 가드·웹의 네이티브 결제 초기화·격리 실행 도구, 구형 로컬 컨테이너 복구 및 연결 문서다. 기존 보안 변경 전체의 재감사 결과로 확대하지 않는다.
